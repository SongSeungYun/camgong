# 마감 확정 측정 (005, 기록용)

헌법 II의 비교 측정 대상은 아니고, SC-001(확정 지연)과 SC-007(대량 처리와 조회 영향)의 수치를 환경과 함께 남긴다.

## 환경

한 대의 Apple M5(10코어, 32GB)에서 앱(`java -Xms512m -Xmx512m -jar`, `benchmark` 프로파일 → 풀 20; jar는 Java 21 툴체인으로 컴파일, 실행은 PATH의 JDK 25), MySQL 8.4 컨테이너(OrbStack), k6(`grafana/k6` 컨테이너)를 모두 돌렸다. 스케줄러는 기본 설정(`interval=30s`, `margin=1s`, `batch-size=100`, `max-rounds=50`). 시드: `load/seed.sql`(회원·세션), `load/seed-close.sql`(공구, 개설자 9 + 참여자 2명 각 3, 총 24 중 15 확보 — 미충족). 일회성 측정이며 반복 횟수는 1회다.

## SC-001 확정 지연

마감 시각이 앞으로 15~90초에 균등하게 흩어진 공구 50개를 시드하고 앱을 띄운 채 기다렸다. 지연 = `updated_at`(확정 시각) − `deadline`.

| 공구 | 확정됨 | 지연 최소 | 평균 | 최대 |
|------|--------|-----------|------|------|
| 50 | 50 (실패 0) | 1.8초 | 15.2초 | 30.1초 |

최대가 30.1초이므로 95%는 목표(1분 이내)를 충족한다. 최악 지연은 이론상 `주기 30초 + 안전 여유 1초 + 처리 시간`이고 측정값은 그 안에 있다. 실행 로그: `close-run closed=14 / 19 / 17 … rounds=1 durationMs=131~155`.

## SC-007 대량 처리와 조회 영향

공구 1,000건의 마감 시각을 모두 같은 순간(시드 후 20초)으로 두고, 앱이 도는 동안 k6(5 VU, 75초)로 목록(모집 중, 모집 실패 50건)과 상세(로그인 쿠키)를 계속 읽었다.

| 항목 | 결과 | 목표 |
|------|------|------|
| 1,000건 확정 완료 | **3.4초** (`close-run closed=1000 skipped=0 failed=0 rounds=10 durationMs=3420`) | 10분 이내 |
| 확정 중 목록 p95 / p99 | 1.6ms / 2.5ms | 1초 이내 |
| 확정 중 상세 p95 / p99 | 3.5ms / 4.7ms | 1초 이내 |
| 요청 수 / 실패 | 232,635건 / 0 | |

확정 전 조회와의 비교는 하지 않았다(확정이 3.4초 만에 끝나 75초 중 대부분이 확정 뒤의 조회다). 확정 구간만의 지연은 따로 분리하지 않았다.

## 후보 조회 인덱스 (T023)

`EXPLAIN`(공구 1만 건): 후보 조회 `WHERE status='OPEN' AND deadline <= … ORDER BY deadline LIMIT 100`은 `idx_group_buy_status_deadline`을 `range`로 탄다(`Using index condition`). 건별 선점은 기본키(`id = :id`) 조회다.

## 한계
