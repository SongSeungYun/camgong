# 마감 확정 측정 (005, 기록용)

헌법 II의 비교 측정 대상은 아니고, SC-001(확정 지연)과 SC-007(대량 처리와 조회 영향)의 수치를 환경과 함께 남긴다.

## 환경

한 대의 Apple M5(10코어, 32GB)에서 앱(`java -Xms512m -Xmx512m -jar`, `benchmark` 프로파일 → 풀 20; jar는 Java 21 툴체인으로 컴파일, 실행은 PATH의 JDK 25), MySQL 8.4 컨테이너(OrbStack), k6(`grafana/k6` 컨테이너)를 모두 돌렸다. 스케줄러는 기본 설정(`interval=30s`, `margin=1s`, `batch-size=100`, `max-rounds=50`). 시드: `load/seed.sql`(회원·세션), `load/seed-close.sql`(공구, 개설자 9 + 참여자 2명 각 3, 총 24 중 15 확보 — 미충족). 일회성 측정이며 반복 횟수는 1회다.

## SC-001 확정 지연

마감 시각이 앞으로 15~90초에 균등하게 흩어진 공구 50개를 시드하고 앱을 띄운 채 기다렸다. 지연 = `updated_at`(확정 시각) − `deadline`.

| 공구 | 확정됨 | 지연 최소 | 평균 | 최대 |
|------|--------|-----------|------|------|
| 50 | 50 (실패 0) | 1.8초 | 15.2초 | 30.1초 |

최대가 30.1초이므로 95%는 목표(1분 이내)를 충족한다. 이론상 최악은 `주기 30초 + 안전 여유 1초 + 처리 시간`(약 31초)이고, 측정값은 그 안에 있다. 단 후보가 다른 인스턴스에 잡혀 `SKIPPED`되면 한 주기를 더 기다리므로 최악은 약 61초 이상이 될 수 있다(이번 측정은 단일 인스턴스라 겪지 않았다).
한계: 지연은 `updated_at`(그 실행 **라운드의 시작 시각** `now`) 기준이라 실제 커밋 시각보다 조금 이르게 기록된다 — 지연이 약간 **과소 측정**된다(이번 실행들의 처리 시간은 131~155ms라 영향은 작다). 실행 로그: `close-run closed=14 / 19 / 17 … rounds=1 durationMs=131~155`.

## SC-007 대량 처리와 조회 영향

공구 1,000건의 마감 시각을 모두 같은 순간(시드 후 20초)으로 두고, 앱이 도는 동안 k6(5 VU, 75초)로 목록(모집 중, 모집 실패 50건)과 상세(로그인 쿠키)를 계속 읽었다. 상세 요청의 id는 **시드된 실제 id 범위**(`ID_MIN`~`ID_MAX`, AUTO_INCREMENT가 되돌아가지 않아 1~1,000이 아니다)에서 고르고 **200만 성공으로 센다**.

| 항목 | 결과 | 목표 |
|------|------|------|
| 1,000건 확정 완료 | **5.5초** (`close-run closed=1000 skipped=0 failed=0 rounds=10 durationMs=5456`) | 10분 이내 |
| 측정 구간(75초) 목록 p95 / p99 | 2.3ms / 3.5ms | 1초 이내 |
| 측정 구간(75초) 상세 p95 / p99 | 5.1ms / 6.6ms (전부 200) | 1초 이내 |
| 요청 수 / 실패 | 163,881건 / 0 (목록·모집 실패 목록·상세 검사 모두 100%) | |

**주의: 위 조회 지연은 "확정이 도는 동안만"의 값이 아니라 75초 측정 구간 전체의 값이다.** 확정은 5.5초 만에 끝나 그 구간이 전체의 일부일 뿐이고, 확정 구간만 따로 떼어 비교하지 않았다. 그래서 "확정이 조회에 영향을 주지 않았다"고 단정하지 못하고, "확정을 포함한 75초 동안 조회가 모두 목표 안이었다"까지만 말한다.
앞서 한 번 측정했을 때는 상세 검사가 "200 또는 404"를 통과로 세고 id 범위를 1~1,000으로 가정해, 상세 수치가 실제로 200 경로였는지 확인할 수 없었다. 위 표는 id 범위와 200 검사를 고쳐 다시 측정한 값이며 이전 상세 수치는 버렸다.

## 후보 조회 인덱스 (T023)

`EXPLAIN`(공구 1만 건, 앱이 실제로 보내는 모양 — `secured_quantity < total_quantity`와 `id NOT IN (…)` 포함, 제외 목록이 1개일 때와 20개일 때 모두): 후보 조회 `WHERE status='OPEN' AND deadline <= … AND secured_quantity < total_quantity AND id NOT IN (…) ORDER BY deadline LIMIT 100`은 `idx_group_buy_status_deadline`을 `range`로 탄다(`Using index condition; Using where`, 정렬은 인덱스 순서라 filesort 없음). 건별 선점은 기본키(`id = :id`) 조회다.

## 경쟁 테스트 1,000회 반복

`CloseRaceIT`(마지막 자리 참여·마감 연장·개설자 취소·참여 이탈·수량 변경으로 가득 채우기가 각각 확정과 동시에)를 `-Drace.repeat=1000`으로 한 번 돌렸다. 종료 상태가 정확히 하나가 아닌 공구, 잘못 확정된 공구(마감 전 `FAILED`·가득 찼는데 `FAILED`), I1 위반은 0건이다. 두 순서가 모두 나왔다(참여가 이긴 853 / 확정이 이긴 147, 취소 902 / 98, 연장 862 / 138). 처음 돌렸을 때 이탈 테스트가 한 번 실패했는데, 원인은 구현이 아니라 테스트의 가정이었다 — 이탈이 락을 쥔 순간 확정이 도착하면 `SKIP LOCKED`로 건너뛰므로 그 라운드의 공구는 다음 실행까지 `OPEN`이다(설계대로). 테스트가 건너뛴 경우 다음 실행을 호출해 `FAILED`가 되는지 확인하도록 고쳤다. 순서를 결정적으로 고정한 확인은 `CloseOrderedRaceIT`(두 순서 모두)가 따로 한다.

## 한계

- 일회성 측정(반복 1회), 한 기계에서 앱·DB·k6 동거.
- 스케줄러가 켜진 단일 인스턴스만 측정했다. 여러 인스턴스의 중복 방지는 `CloseConcurrencyIT`가 **검증**하지만(`CloseOrderedRaceIT`는 확정 하나와 요청 하나의 순서를 고정할 뿐 두 확정 실행을 겹치지는 않는다), 한 JVM·한 커넥션 풀·같은 `Clock` 안에서 스레드로 흉내 낸 것이다(서로 다른 서버의 시계 오차나 네트워크 지연은 재현하지 못한다).
- 조회 지연은 확정이 끝난 뒤의 구간을 포함한 75초 전체 값이다(위 SC-007 주의 참고).
