# 알림 대량 생성 측정 (007, 기록용)

헌법 II의 비교 측정 대상은 아니고 SC-005(수신자 1,000명 사건의 알림이 5분 안에 생성), SC-006(알림 목록 95%가 1초 이내), 그리고 사건을 일으킨 요청이 알림 생성을 기다리지 않는다는 요구(FR-012)의 수치를 환경과 함께 남긴다.

## 환경과 방법

한 대의 Apple M5(10코어, 32GB)에서 앱(`java -Xms512m -Xmx512m -jar`, `benchmark` 프로파일 → 풀 20; jar는 Java 21 툴체인으로 컴파일, 실행은 PATH의 JDK 25), MySQL 8.4 컨테이너(OrbStack), k6(`grafana/k6` 컨테이너)를 모두 돌렸다. 알림 실행기는 기본 설정(core 2, max 4, queue 1000, 배치 청크 500, 비동기 켬). 시드: `load/seed.sql` + `load/seed-notify.sql`(개설자 1명 + 참여자 1,000명인 공구 1건).

## 결과

| 항목 | 결과 | 목표 |
|------|------|------|
| 사건(개설자의 공구 취소)을 일으킨 요청의 응답 시간 | 0.11초 (204, 콜드 첫 요청) | 알림이 없을 때와 비슷, 95%가 1초 이내 |
| 알림 1,000건 생성 완료까지(요청 시작 → 행 1,000개 확인) | 0.42초 | 5분 이내 (SC-005) |
| 생성된 알림 | 1,000건, 수신자 1,000명 모두 서로 다름 (중복 0) | |
| 알림 목록(+읽지 않은 개수) 응답 p95 / p99 | 3.95ms / 5.15ms (51,110 요청, 실패 0) | 1초 이내 (SC-006) |

요청이 알림 생성을 기다리지 않는다는 것은 시간 비교가 아니라 `NotificationAsyncIT`가 결정적으로 증명한다: 알림 쓰기를 붙잡아 둔 채로도 요청 응답이 1초 안에 나가고 쓰기를 풀어 주면 그제야 알림이 생긴다. 큐가 가득 차면(`NotificationQueueFullIT`) 알림은 유실로 취급되고 요청은 영향을 받지 않는다(허용된 한계).

## 한계

- 일회성 측정(반복 1회), 한 기계에서 앱·DB·k6 동거. 응답 시간은 콜드 첫 요청 하나라 안정적인 분포가 아니다("알림이 없을 때"와의 직접 비교는 하지 않았다).
- 생성 시간은 1,000건 한 사건(청크 2개)만 쟀다. 여러 사건이 동시에 몰리는 경우는 측정하지 않았다.
- 목록 응답 시간은 회원당 알림이 1건인 상태다(회원당 수백 건일 때의 키셋 페이지 비용은 `KEY (recipient_id, id)`에 기댄다).
