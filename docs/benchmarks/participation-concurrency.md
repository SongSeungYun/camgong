# 참여 수량 게이트 4방식 비교 (헌법 II)

같은 요구(확보 수량이 총 수량을 넘지 않고, 모집 완료 전환이 한 번)를 지키는 네 가지 동시성 방식을 같은 시나리오·같은 환경으로 측정했다. 기능 정확성은 `QuantityRaceTests` 등 통합 테스트가 안전한 3방식으로 따로 지킨다. 여기서는 **성능과, 일부러 틀리게 만든 대조군이 실제로 어떻게 깨지는지**를 본다.

## 방식

| 이름 | 구현 | 요지 |
|------|------|------|
| `none` | `NoLockQuantityGate` | 일반 SELECT로 읽고 자바에서 검사한 뒤 `읽은 값 + delta`를 쓴다. **일부러 틀린 대조군** (`benchmark` 프로파일에서만 켜진다) |
| `pessimistic` | `PessimisticQuantityGate` | `SELECT … FOR UPDATE`로 공구 행을 잡고 검사·갱신. 같은 공구 요청이 락으로 직렬화된다. **현재 기본값** |
| `optimistic` | `OptimisticQuantityGate` | 락 없이 읽고 `@Version`(`WHERE version = ?`) 충돌로 감지. 충돌하면 새 트랜잭션에서 **최대 3회 시도**(첫 시도 + 재시도 2번, 시도 사이 5~25ms 무작위 대기, 백오프 없음), 소진하면 `BUSY`(409) |
| `conditional` | `ConditionalUpdateQuantityGate` | 한 문장의 조건부 `UPDATE`(상태·마감·가격·남은 수량을 `WHERE`가 판정). 영향 행 0이면 이유를 `FOR SHARE`로 진단 |

## 환경과 방법

- 한 대의 Apple M5(10코어, 32GB) 위에서 앱(`java -Xms512m -Xmx512m -jar`; jar는 `build.gradle`의 Java 21 툴체인으로 컴파일했고 실행은 PATH의 JDK 25로 했다), MySQL 8.4 컨테이너(OrbStack), k6(`grafana/k6` 컨테이너)를 모두 돌렸다. 세 프로세스가 CPU를 나눠 쓴다.
- 커넥션 풀 20(`application-benchmark.yml`), JVM 힙 512MB 고정, 측정 중 다른 작업 없음. 방식마다 앱을 새로 띄웠다(같은 DB 컨테이너, 시나리오마다 공구 행을 새로 만듦).
- 인증은 시드한 세션 쿠키(`load/seed.sql`)로 한다. 회원 101명.
- 시드·시나리오·실행: `load/seed.sql`, `load/reset.sql`, `load/k6/{last-seat,s2,mixed}.js`, `load/run-bench.sh`, `load/run-all.sh`. 결과 CSV를 `load/bench_report.py`가 아래 표로 만든다. 앱 지표(재시도 수, BUSY, 모집 완료 이벤트 수)는 `benchmark` 프로파일의 `/bench/stats`에서 읽는다. 모집 완료 이벤트 수는 커밋 전에 세므로 **발행 시도 횟수**다(롤백된 시도도 포함하며, 커밋된 이벤트 수와 다를 수 있다).
- 시나리오마다 불변식 검증 쿼리(data-model.md의 I1)를 실행해 `secured_quantity ≠ Σ participation.quantity`인 공구를 센다.

시나리오
- **S1 마지막 자리**: 남은 수량 1, 서로 다른 100명이 동시에 1개씩. 성공은 정확히 1건이어야 한다.
- **S2 다양한 수량**: 남은 수량 10, 50명이 동시에 1~5개(요청자 번호로 수량을 정해 방식끼리 같은 요청을 받는다). 성공 수량 합이 10을 넘으면 안 된다.
- **혼합 부하**: 회원 20명이 참여·수량 변경·참여 취소를 무작위로 하고, 개설자가 공구를 수정한다. 같은 공구 행에 쓰기가 계속 몰린다.

## 해석

**정확성 (대조군이 깨지는 모습)**
- `none`은 예상대로 깨졌다. S1에서 30회 모두 성공이 정확히 1건이 아니었고(성공 수 합계 446건, 반복당 평균 15건) I1 위반(확보 수량 ≠ 참여 합)이 30회 전부, 모집 완료 이벤트가 정확히 1번이 아닌 반복도 30회 전부였다. S2에서는 수용 수량이 평균 131(한도 10)이었고 총 수량(24)을 넘는 참여 합이 30회 전부 나왔다. 확보 수량 컬럼은 갱신 손실로 `CHECK`를 통과하는 값에 머무르는 동안 참여 행은 계속 쌓였다. 혼합 부하에서도 5회 모두 I1이 깨졌고 5xx가 180건 났다(원인은 확인하지 않았다. 초과한 확보 수량이 `CHECK`에 걸린 것으로 **추정**하지만 오류 본문을 남기지 않았다).
- 나머지 세 방식은 S1·S2·혼합 모두 I1 위반 0, 초과 0, 모집 완료 전환 정확히 1번, 5xx 0이다.

**성능**
- S1·S2의 지연은 `pessimistic`, `conditional`이 비슷하다(S1 p95 중앙 70.0 / 75.7ms, S2 47.5 / 49.0ms). `conditional`은 락 대기를 `UPDATE`의 행 잠금이 대신하므로 단일 행 경합에서는 `pessimistic`과 같은 직렬화 비용을 낸다.
- `optimistic`은 S1에서 가장 빨랐다(p95 중앙 54.0ms). 99건이 곧바로 거부되는 시나리오라 재시도가 적다(재시도 404회/30회 반복). 하지만 S2처럼 성공이 여럿인 경쟁에서는 재시도가 늘었고(1,684회) **3회 시도를 모두 소진해 `BUSY`로 거부된 요청이 12건 생겼다**. 이 `BUSY`는 "남은 수량이 없어서"가 아니라 "충돌이 심해서" 나온 거부라 사용자에게 억울한 실패다.
- 혼합 부하(같은 행에 쓰기가 계속 몰림)에서 `optimistic`은 요청의 **약 50%(83,242건 중 41,969건)가 `BUSY`**로 거부됐고(3회 시도·5~25ms 무작위 대기·백오프 없음이라는 현재 재시도 설정에서의 결과다. 시도 횟수·대기를 늘리면 줄어들 수 있지만 그만큼 락 없는 방식의 장점이 사라진다) 재시도 합계가 124,484회였다. 처리량 숫자는 이 거부된 요청을 포함해서 높게 보이므로 비교에 쓰면 안 된다. `pessimistic`(478 req/s)과 `conditional`(472 req/s)은 BUSY가 0이고 서로 거의 같다.
- 혼합 부하에서 `none`의 처리량·지연이 가장 좋아 보이는 것(664 req/s, p50 29.1ms)은 아무것도 지키지 않기 때문이다. 다만 `none`은 거의 모든 요청을 수용해(S2 평균 131개 수용, 다른 방식은 10개) 하는 일 자체가 달라서, 지연을 다른 방식과 직접 비교할 수는 없다. S1에서는 `optimistic`(p50 40.5ms)이 `none`(44.1ms)보다 빨랐다.

**주의 (측정의 한계)**
- 한 기계에서 앱·DB·k6가 CPU를 나눠 쓰므로 절대값은 실제 서버와 다르고, 방식 사이의 순서와 정확성 결과가 의미 있는 부분이다.
- 첫 번째 혼합 부하 측정은 총 수량을 24로 두어 공구가 곧 모집 완료가 됐고, 이후 요청이 모두 빠른 `NOT_JOINABLE` 거부가 되어 비교가 무의미했다(`optimistic`이 가장 빨라 보였다). 이를 알아채고 총 수량 200으로 바꿔 혼합 부하만 다시 측정했다. 위 표는 다시 측정한 값이다(첫 측정의 결과 파일은 보존하지 않았다).
- 혼합 부하는 계획의 60초 × 30회가 아니라 30초 × 5회다(시간 제약). S1·S2는 30회 반복.
- S1에서 최악 p95/p99가 모든 방식에서 208~214ms로 반복해서 같은 값이 나온다. 반복의 첫 요청에 몰리는 하네스 쪽 요인(연결 수립·JIT 등)으로 **추정**하지만 확인하지 않았다. 그래서 지연은 중앙값(S1·S2)으로 비교했다. 혼합 부하는 반복이 5회뿐이라 평균으로 집계했다(S1·S2는 중앙값, 혼합은 평균 — 집계 방식이 다르다).
- 혼합 부하의 총 수량은 200이라 공구가 계속 열려 있어 **거부 경로(남은 수량 부족)를 거의 거치지 않는다.** 쓰기 경합의 처리량을 보는 시나리오이고, 거부가 몰리는 경우는 S1·S2가 대신한다.
- 실행 순서를 `none → pessimistic → optimistic → conditional`로 고정했다. 순서 효과(캐시, 온도, 백그라운드 부하)를 배제하지 못했다.
- 한 공구에 요청이 몰리는 최악의 경합만 봤다. 공구가 여럿이고 요청이 흩어지면 방식 간 차이는 줄어든다(락과 충돌이 공구 단위이므로).

## 마지막 자리 1,000회 반복 (SC-002)

정확성 테스트 `QuantityRace*IT.lastSeatGoesToExactlyOneOfOneHundred`(남은 1, 100명 동시)를 안전한 세 방식 각각 `-Drace.repeat=1000`으로 1,000라운드씩 돌렸다(`build.gradle`이 이 속성을 테스트 JVM에 넘긴다 — 이 연결을 추가하기 전에는 속성이 전달되지 않아 기본 20회만 돌았다는 점을 이 단계에서 확인해 고쳤다). 라운드마다 성공 정확히 1건, 나머지는 409(`NOT_JOINABLE`/`INSUFFICIENT_QUANTITY`/`BUSY`), 모집 완료 이벤트 정확히 1회, I1·I2 위반 0을 단언한다.

| 방식 | 라운드 | 결과 | 소요 |
|------|--------|------|------|
| pessimistic | 1,000 | 모두 통과 (위반 0) | 82초 |
| conditional | 1,000 | 모두 통과 (위반 0) | 85초 |
| optimistic | 1,000 | 모두 통과 (위반 0) | 74초 |

## 선택

**최종 운영 방식은 사용자가 정한다.** 기본값은 그때까지 `pessimistic`이다. 측정으로 알 수 있는 것:

- `none`은 탈락(정확성이 깨진다).
- `optimistic`은 이 서비스의 부하 모양(한 공구에 마지막 자리·인기 공구로 요청이 몰림)과 맞지 않는다. 충돌이 잦아 정상 요청이 `BUSY`로 거부되고, 재시도 횟수·대기 시간이라는 튜닝 대상이 생긴다. 충돌이 드문 읽기 많은 갱신에 맞는 방식이다.
- `pessimistic`과 `conditional`은 정확성도 지연도 거의 같다. 차이는 코드 모양이다: `pessimistic`은 객체 모델(엔티티 상태 전이 `completeIfFull`)을 그대로 쓰고 락 순서(공구 → 참여)가 001 수정·취소와 같아 추론이 쉽다. `conditional`은 MySQL 전용 문법(`IF`, `SET` 평가 순서)과 `useAffectedRows=true`에 기대고 거부 사유를 진단하는 쿼리가 더 필요하지만, 락을 따로 잡지 않는다.
- 추천: `pessimistic` 유지. 이유는 위와 같다. 지연 차이가 없고 설명하기 쉽다. (확정은 사용자 결정 뒤에 이 절에 이유와 함께 적는다.)
