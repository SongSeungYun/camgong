# 캠공 Constitution

## Core Principles

### I. 범위 상한 (NON-NEGOTIABLE)
MVP는 공구 개설, 참여/취소, 목록·상세, 마감 시 성공/실패 확정과 알림, 개설자용 참여자·입금·수령 체크로 한정한다.
결제 연동은 MVP에 포함하지 않는다. 일정이 막히면 화면, 배포 순서로 먼저 줄이고 핵심 API와 측정은 줄이지 않는다.
각 단계는 시간 상한을 두며, 1단계(요구사항·설계)는 4~5시간을 넘기지 않는다.
근거: 사이드 프로젝트라 끝까지 가는 것이 기능 수보다 중요하다.

### II. 측정으로 증명
성능·동시성 주장은 전후 수치 없이 완료로 인정하지 않는다.
- N+1: 같은 시나리오에서 개선 전후 쿼리 수를 기록한다.
- 동시성: 마지막 자리 경쟁을 락 없음 / 비관적 / 낙관적 / 조건부 UPDATE로 구현해 k6로 비교한다.
- 측정 방법, 환경, 결과는 저장소 문서로 남긴다.
근거: 이 프로젝트의 목적은 N+1·동시성을 직접 풀고 수치로 설명하는 것이다.

### III. 설명 가능한 설계
설계 결정(스키마, 락 방식, 쿼리 전략 등)은 대안과 선택 이유가 plan 문서에 적혀 있어야 통과한다.
작성자는 결정 이유를 자기 말로 설명할 수 있어야 하며, 설명하지 못하는 결정은 확정하지 않는다.
근거: 포트폴리오·면접에서 "왜 그렇게 했는가"에 답할 수 있어야 한다.

### IV. 핵심 로직 테스트
다음 로직은 Testcontainers(MySQL) 기반 통합 테스트를 MUST 갖는다: 정원 초과 판정, 마감 성공/실패 확정,
동시 참여 경쟁, 마감 스케줄러 중복 실행 방지. 그 외 코드의 테스트는 선택이며 의무가 아니다.
테스트는 H2가 아닌 실제 MySQL 컨테이너에서 실행한다(락·격리 수준 동작이 다르기 때문).

## 기술 제약

- 언어/프레임워크: Java 21, Spring Boot.
- DB: MySQL. 스키마 변경은 마이그레이션 또는 문서로 추적 가능해야 한다.
- 테스트: Testcontainers.
- 새 외부 의존성(라이브러리, 인프라)은 필요한 이유를 plan에 한 줄로 적고 추가한다.

## 개발 워크플로

- Spec Kit 흐름은 constitution → specify → plan → tasks까지 사용한다. implement 단계는 사용하지 않는다.
- 단계 순서: 1 요구사항·설계 → 2 핵심 API + N+1 → 3 마감 + 동시성 측정 → 4 로그인/화면/Docker → 5 실제 공구 운영·수치 수집.
- 요구사항 답변과 설계 결정은 작성자가 직접 내린다. 문서를 승인만 하는 방식은 허용하지 않는다.

## Governance

이 헌법이 다른 작업 방식보다 우선한다. 1인 프로젝트이므로 개정에 별도 승인 절차는 없으며,
개정 시 버전, 날짜, 변경 이유를 기록한다.

- 버전 규칙: MAJOR는 원칙 삭제·재정의, MINOR는 원칙/섹션 추가·확장, PATCH는 문구 정리.
- plan 작성 시 각 원칙(특히 I, II)에 대한 준수 여부를 확인한다. 위반하려면 이유를 plan에 적는다.
