# Quickstart: 마감 확정 검증

구현 후 이 기능이 end-to-end로 동작하는지 확인하는 시나리오다. 규칙은 [data-model.md](data-model.md), 이벤트·설정은 [contracts/events-and-config.md](contracts/events-and-config.md)를 본다.
001(개설), 004(참여), 003(조회)이 구현되어 있어야 화면 쪽 결과까지 볼 수 있다. 시간은 테스트의 `MutableClock`으로 움직인다.

## 준비

- 001 quickstart의 준비(JDK 21, Docker). 테스트 프로파일은 `camgong.scheduler.close.enabled=false`로 두고 `GroupBuyCloseService.closeExpired()`를 직접 호출한다.
- 공구 시드: 총 24, 개설자 수량 9, 마감 `T`. 상태별로 여러 개 만든다.
- 자동 테스트: `./gradlew test`.

## 시나리오

| # | 확인 내용 | 조작 | 기대 결과 | spec |
|---|-----------|------|-----------|------|
| 1 | 정상 확정 | 마감이 지난 수량 미충족 공구, `now = T + 2초`에서 확정 실행 | `FAILED`, 이후 참여·변경·취소·수정 모두 409 | US1-1, FR-002 |
| 2 | 마감 전 | `now = T − 1초`에서 실행 | 변화 없음 | US1-2, SC-003 |
| 3 | 완료·취소·이미 실패 | 같은 시각에 `COMPLETED`, `CANCELLED`, `FAILED` 공구 | 모두 변화 없음, 이벤트 없음 | US1-3, FR-001 |
| 4 | 마감 정각과 안전 여유 | `now = T`에서 실행 → 참여는 즉시 거부, 확정은 안 됨. `now = T + 1초`에서 실행 → 확정 | `T`에서는 `OPEN` 유지(참여는 409), `T + 1초`에 `FAILED` | US1-4, FR-005 |
| 5 | 이벤트 | 개설자 + 참여자 2명 공구를 확정 | `GroupBuyFailed` 1건, 대상 3명 | US1-5, FR-004 |
| 6 | 표시 | 확정 후 003 목록(모집 실패 필터), 내 활동, 상세의 오픈채팅 링크 | '모집 실패' 표시, 링크 비공개, 참여 기록 보존 | US1-6, FR-003 |
| 7 | 개설자만 | 참여자 없는 공구 확정 | `FAILED`, 이벤트 대상 1명(개설자) | US1-7 |
| 8 | 여러 인스턴스 | 마감된 공구 100개, 스레드 5개가 동시에 `closeExpired()` | 100개 모두 `FAILED`, 각 공구 확정·이벤트 정확히 1회. 1,000번 반복해도 중복 0 | US2-1, SC-002 |
| 9 | 겹친 실행 | 한 실행이 끝나기 전 다음 실행 시작 | 같은 공구를 두 번 처리하지 않음 | US2-2 |
| 10 | 재실행 | 이미 `FAILED`인 공구에 다시 실행 | 아무 일도 없음, 이벤트 재발행 없음 | US2-3 |
| 11 | 마지막 참여 vs 확정 | `now`가 마감 직전/직후인 공구에 마지막 수량 참여와 확정을 동시에 | 처리 시점이 마감 전이면 `COMPLETED`(확정 대상 아님), 이후면 참여 409 후 `FAILED`. 두 상태를 동시에 갖는 공구 0건(1,000번 반복) | US3-1·2, SC-006 |
| 12 | 연장 vs 확정 | 마감 직전 개설자가 마감 연장, 확정과 동시에 | 연장이 마감 전에 처리되면 `FAILED` 아님, 이후면 연장 409 후 `FAILED` | US3-3 |
| 13 | 취소 vs 확정 | 마감 직전 개설자 취소와 확정 동시에 | `CANCELLED`와 `FAILED` 중 정확히 하나 | US3-4 |
| 14 | 일부 실패 격리 | 공구 10개 중 1개의 확정이 예외(테스트에서 이벤트 리스너·서비스 모킹으로 유발) | 9개 `FAILED`, 1개는 `OPEN` 유지·WARN 로그, 다음 실행에서 재시도해 성공하면 이벤트 1회 | US4-2·3, FR-008 |
| 15 | 밀린 공구 | 스케줄러를 끈 채 50개를 마감시킨 뒤 `closeExpired()` | 50개 모두 `FAILED`, 마감 시각이 이른 순으로 처리 | US4-1, FR-006 |
| 16 | 스케줄러 연결 | `enabled=true`로 컨텍스트를 띄우고 마감된 공구를 둠 | 주기 안에 스스로 확정됨 | FR-006 |
| 17 | 기록 | 시나리오 1 직후 로그 | `close-run closed=1 skipped=0 failed=0 …` 한 줄 | FR-012 |

## 측정 (기록용, 헌법 II 대상은 아님)

SC-001·SC-007 수치를 문서로 남긴다. `docs/benchmarks/close-batch.md`에 환경과 함께 적는다.

| 측정 | 방법 | 목표 |
|------|------|------|
| 확정 지연 | 공구 마감 시각과 `FAILED`가 된 시각의 차이, 스케줄러 켠 채 50개를 무작위 시각에 마감 | 95%가 1분 이내 (SC-001) |
| 대량 처리 | 공구 1,000건을 같은 시각에 마감시키고 완료까지 시간 | 10분 이내 (SC-007) |
| 조회 영향 | 위 처리 중 k6로 목록·상세 조회 | 95%가 1초 이내 (SC-007) |

```bash
./gradlew bootRun --args="--camgong.scheduler.close.enabled=true"
# 시드: 마감이 지난 공구 1,000건 삽입 후 로그의 close-run 줄과 소요 시간 확인
k6 run load/k6/list-during-close.js
```
