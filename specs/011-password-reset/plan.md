# Implementation Plan: 비밀번호 재설정

**Branch**: `011-password-reset` | **Date**: 2026-11-22 | **Spec**: [spec.md](spec.md)

## Summary

로그인 화면에서 학교 이메일로 재설정을 요청하면 가입한 회원에게만 1시간짜리 일회용 링크를 보낸다. 응답·한도·응답 시간으로 가입 여부를 드러내지 않는다. 링크에서 새 비밀번호를 정하면 모든 세션을 끝내고 로그인 실패 잠금을 푼 뒤 로그인 화면으로 보낸다.

## Technical Context

Java 21, Spring Boot 4.1.2, MySQL 8.4(Flyway V4), React/Vite/TS. 002의 `Tokens`, `Keys`, `SchoolDomains`, 메일 발송(`MailSender`), `LoginService`(실패 기록), `SessionService`를 쓴다. 새 외부 의존성 없음.

## Constitution Check

- I. 범위 상한: 002가 범위 밖으로 둔 기능을 더한다. 사용자 결정(2026-11-22 "다시 본인인증하면되지", "비밀번호 재설정")이다. 탈퇴(010)를 비밀번호를 잊은 회원도 쓰게 하려는 것이라 배포 전 필요하다. 통과.
- II. 측정: 성능 주장 없음. 해당 없음.
- III. 설명 가능: 아래 결정마다 대안과 이유. 통과.
- IV. 핵심 로직 테스트: 의무 대상은 아니지만 한도·일회용·동시성은 Testcontainers 통합 테스트로 덮는다.

## 결정 (research)

### 1. 저장 — `password_reset` 표 하나(주소당 한 줄)
- `member`에 `password_changed_at DATETIME(6) NULL`을 더한다(결정 3).
- 열: `email_key`(PK), `member_id`(NULL 가능), `token_hash`(NULL 가능, CHAR(64)), `token_expires_at`, `used_at`, `last_sent_at`, `window_started_at`, `sent_count`, `created_at`. `token_hash` 인덱스.
- 주소마다 한 줄이고 가입 여부와 상관없이 만든다. 한도를 가입 여부와 무관하게 세기 위해서다(FR-004). 회원이 아니면 `member_id`·`token_hash`가 NULL이고 메일을 보내지 않는다.
- 대안: 회원에게만 줄을 만들기 → 회원 아닌 주소는 한도에 안 걸려 429 여부로 가입이 드러난다. 탈락. `pending_signup`에 합치기 → 가입 신청 규칙(재발송, 409)과 섞여 설명이 어렵다. 탈락.
- 회원 아닌 주소도 남는 것은 `login_attempt`와 같은 이유(남용 방어)다. 마지막 요청부터 1일 뒤 정리한다(결정 7).

### 2. 요청 `POST /api/auth/password-reset` — 늘 같은 202
- 이메일 형식·대학 메일 검사는 가입과 같다(400 `errors[email]`, 가입 여부와 무관한 규칙).
- 한도: 가입 인증 메일과 같은 설정(`resend-interval` 1분, `daily-limit` 24시간 5회)과 같은 조건부 UPDATE 모양(`SignupService`의 IF 창). 넘으면 429 `TOO_MANY_REQUESTS` + `retryAt`. 회원 여부와 상관없이 같은 줄로 센다.
- 한도 안이면: 회원(탈퇴 안 함, `withdrawn_at IS NULL`)이면 새 토큰을 만들어 해시만 저장하고(이전 토큰 덮어씀, FR-005) 메일 이벤트를 낸다. 아니면 토큰 열을 비운다. 응답은 둘 다 `202 { "retryAt": … }`.
- **메일은 요청 스레드 밖에서 보낸다(비동기).** 요청 스레드에서 보내면 회원 주소만 SMTP 시간(수백 ms~수 초)만큼 느려 응답 시간으로 가입이 드러난다(FR-003). 가입 인증 메일이 이미 쓰는 길(커밋 뒤 `VerificationMailListener`가 `mailExecutor`에 넘김, 002)을 그대로 쓴다. (2026-11-25 고침: 처음 판에는 가입 메일이 요청 스레드에서 나간다고 잘못 적었다. 테스트만 `SyncTaskExecutor`다.) 발송 실패는 응답에 영향이 없고 WARN만 남긴다(가린 주소, 기존 `mask`).
- 남은 차이(받아들임): 회원 주소만 회원 행을 `FOR SHARE`로 한 번 더 읽는다(탈퇴와 같은 잠금 순서, 아래 4). 1밀리초 안쪽 차이이고 429 응답으로 무제한 잴 수 있지만, 가입 신청의 409가 이미 가입 여부를 바로 알려 주므로 새로 드러나는 것은 없다(spec Assumptions).
- 대안: 응답을 일정 시간 늦추기 → 모든 요청이 느려지고 SMTP 지연이 그보다 길면 다시 드러난다. 탈락.

### 3. 확인 `POST /api/auth/password-reset/confirm` — 가입 확인과 같은 오류 모양
- 본문 `{ token, password }`. 화면은 링크를 열면 폼만 보여주고 제출할 때 보낸다(검증 화면과 같다, 008).
- 순서: 토큰 해시로 줄 찾기 → 없으면 400 `INVALID_TOKEN` → `used_at` 있으면 409 `TOKEN_USED` → 만료면 410 `TOKEN_EXPIRED` → 비밀번호 검사(002 가입 규칙, 400 `errors[password]`, 토큰 그대로) → 트랜잭션.
- 트랜잭션: `member` 행 `FOR UPDATE`(010과 같은 잠금 순서: 회원 먼저) → 탈퇴했으면 400 `INVALID_TOKEN` → `password_hash` 바꾸기, `used_at` 기록, 그 주소의 `login_attempt` 삭제(FR-007, 009 잠금 해제). 토큰 행도 `FOR UPDATE`로 다시 읽어 `used_at`을 확인한다(같은 링크 두 번 동시 제출 → 하나만 204, 하나는 409).
- **세션 끊기**(FR-007, SC-002): 세 가지를 함께 한다.
  1. `member.password_changed_at`(V4에서 더함, NULL 가능)을 이 트랜잭션에서 기록한다. 세션을 확인하는 곳(`AuthFilter`가 쓰는 세션 조회)은 `login_session.created_at < member.password_changed_at`인 세션을 없는 세션처럼 다루고 지운다. 그래서 커밋 뒤 세션 삭제가 실패해도 옛 세션은 쓸 수 없다.
  2. 로그인의 세션 INSERT는 "검증한 비밀번호 해시가 그대로일 때만" 넣는다(`INSERT … SELECT … FROM member WHERE id = ? AND password_hash = :검증한 해시`). 옛 비밀번호로 로그인하던 요청이 재설정 커밋 직후 세션을 넣는 경쟁을 막는다: 이 SELECT는 회원 행을 읽으며 재설정 트랜잭션을 기다리고, 커밋 뒤에는 해시가 달라 아무것도 넣지 않는다(그 로그인은 401). 1번만으로는 이 경쟁을 못 막는다(세션 생성 시각이 변경 시각보다 늦다).
  3. 커밋 뒤 그 회원의 세션 중 `password_changed_at`과 같거나 먼저 만든 것을 지운다(같은 시각은 순서를 모르므로 지운다, 다시 로그인하면 된다)(탈퇴와 같은 이유로 트랜잭션 밖, 010 결정 5). 새 비밀번호로 막 로그인한 세션은 지우지 않는다(이 삭제가 잠금을 기다리는 사이 생길 수 있다). 실패하면 WARN만 남긴다(1번이 막는다).
  - 대안: 트랜잭션 안에서 세션 삭제 → 로그인 INSERT와 교착할 수 있다(010에서 확인한 모양). 탈락. 세션 삭제만 → 삭제 실패·경쟁 때 옛 세션이 남는다. 탈락.
- 성공 `204`. 자동 로그인하지 않는다(spec Assumptions). 쿠키도 건드리지 않는다.

### 4. 탈퇴·장부와의 관계 (010에 더함)
- 탈퇴 익명화(`erase`)에 `DELETE FROM password_reset WHERE email_key = :key`를 더한다. 장부 재적용도 같은 `erase`를 쓰므로 함께 지운다.
- 재설정 확인과 탈퇴가 동시에 오면 둘 다 회원 행을 먼저 잠가 차례로 처리된다. 탈퇴가 먼저면 확인은 토큰 행이 없어 400 `INVALID_TOKEN`, 확인이 먼저면 탈퇴는 이미 비밀번호를 확인했으므로 그대로 진행한다.

### 5. 링크 주소
- `RESET_LINK_BASE_URL`(기본 `http://localhost:5173/password-reset/confirm?token=`). 운영 compose는 `VERIFY_LINK_BASE_URL`처럼 `DOMAIN`으로 만든다.

### 6. 메일 본문
- 제목 "[캠공] 비밀번호 재설정". 본문: 링크, "1시간 동안 한 번만 쓸 수 있어요", "요청하지 않았다면 이 메일을 무시하세요. 비밀번호는 바뀌지 않아요." 표시 이름은 넣지 않는다.
- 발송 기록은 Gmail 보낸편지함에 남고 `docs/gmail-cleanup.md`가 6일 뒤 지운다.

### 7. 정리
- `SessionCleanup`에서 `last_sent_at`이 24시간보다 오래된 줄을 지운다. 이 조건이면 24시간 창도, 1분 간격도 지났고 토큰(마지막 요청 + 1시간)도 만료됐다. 그래서 요청 기록은 마지막 요청부터 최대 1일 남짓 남는다. (2026-11-25 고침: 처음 판의 `window_started_at` 기준은 창이 막 지난 직후, 마지막 요청 1분 안의 줄을 지웠다. 토큰이 없는 비회원 줄만 지워져 다음 요청이 비회원은 202, 회원은 429가 되어 가입이 드러났다.) 처리방침 4절의 "비밀번호 재설정 요청 기록" 줄은 "마지막 요청부터 1일"로 적는다.

### 8. 로그
- 요청·확인 로그에 이메일을 남기지 않는다. 성공한 재설정은 `password-reset memberId=` INFO만.

## 프론트 (008)

- 로그인 화면에 "비밀번호를 잊었어요" 링크 → `/password-reset`: 학교 이메일 입력 → 202면 "가입한 학교 메일이면 재설정 링크를 보냈어요. 1시간 안에 열어 주세요." + 다시 요청 가능 시각, 429는 남은 시간.
- `/password-reset/confirm?token=`: 새 비밀번호 + 확인 입력 → 204면 `/login`으로 가서 "비밀번호를 바꿨어요. 새 비밀번호로 로그인해 주세요." 안내. 400 `INVALID_TOKEN`·409·410은 토큰 오류 화면(재요청 링크), 400 `errors[password]`는 칸 옆.
- 로그인 상태에서 링크를 열어도 같은 화면이다. 성공하면 세션이 끝나므로 화면 세션도 비운다(`forget`).
- 목(MSW)은 계약 그대로: 가입 여부와 무관하게 같은 202, 같은 한도.

## 검증 (quickstart)

1. 가입한 주소·인증 전·탈퇴·처음 보는 대학 주소로 요청 → 모두 202 같은 본문, 메일은 가입한 주소만.
2. 1분 안에 다시 → 네 주소 모두 429.
3. 링크로 새 비밀번호 → 204, 옛 비밀번호 401, 새 비밀번호 200, 다른 기기 세션 401, 잠긴 회원도 바로 로그인.
4. 같은 링크 다시 409, 1시간 뒤 410, 앞선 링크 400.
5. 응답 시간: 회원·비회원 주소 각 20회 요청의 중앙값 차이가 SMTP 한 번 시간보다 훨씬 작다(로깅 메일로는 의미 없음, 실서버 SMTP로 한 번 확인 — 확인 못 하면 그렇게 적는다).
