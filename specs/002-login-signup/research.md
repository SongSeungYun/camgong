# Research: 회원 가입·로그인·로그아웃

**모든 결정은 2026-10-26에 사용자가 추천안으로 확정했다.** 밤샘 작성이라 사용자에게 물을 수 없었다. 각 결정에 후보와 **추천**, 이유, 설명 체크를 적었고 plan·data-model·contracts·quickstart는 추천안 기준으로 썼다. 사용자가 다른 후보를 고르면 해당 문서를 같이 고친다.

> **변경 B2 (2026-10-28, 사용자 결정 "안 2")**: 신청 단계에서는 이메일만 받고, 표시 이름·비밀번호·동의는 인증 링크를 누른 사람이 인증 단계(`POST /verify`)에서 정한다. 계정 선점(pre-hijacking) 방어가 이유이며 결정 13에 적었다. 아래 결정 중 2·4·12가 이에 맞춰 바뀌었다. 이전 '재제출은 이름·비밀번호 유지'(안 B)는 폐기.

## spec 보완 제안 (설계 중 발견)

plan을 쓰다 보니 spec이 정하지 않은 것이 있다. spec은 수정하지 않았다(밤샘 규칙). 아침에 반영 여부를 정해줘.

1. **비밀번호 최대 길이가 없다.** 추천 해시(BCrypt)는 입력 72바이트를 넘으면 뒷부분을 무시한다. "8자 이상"에 더해 "72바이트 이하(또는 64자 이하)"가 필요하다.
2. **잠금 안내가 계정 존재 여부를 드러낼 수 있다.** FR-010은 존재 여부를 숨기라고 하고 FR-011은 잠금을 알리라고 한다. 실패 횟수를 이메일 키로 세면(없는 계정도) 둘이 모순되지 않는다(결정 7).
3. **인증 링크를 `GET`으로 열면 안 된다.** 메일 보안 스캐너가 링크를 미리 열어 한 번뿐인 토큰을 소진할 수 있다. 링크는 화면을 열고 화면이 `POST`로 확인한다(결정 3). spec의 "링크를 확인한다" 표현과 충돌하지 않는다.
4. **001 이후 모든 테스트가 `X-Member-Id`를 쓴다.** FR-014로 이 헤더가 사라지면 테스트 인증 방식을 한 번에 바꿔야 한다. `as(memberId)` 헬퍼를 지금부터 쓰면 전환이 한 곳에서 끝난다(결정 10).
5. **허용 학교 이메일 도메인의 실제 값**과 **메일 발송 계정**은 사용자 준비물이다(결정 5, 8).

## 결정

### 1. 로그인 상태 유지 방식과 보안 의존성 — 상태: 확정 (추천대로, 2026-10-26)

- **후보**
  - A. **서버 세션**: 세션 id를 `HttpOnly` 쿠키에 담고, 서버 DB(`login_session`)가 상태를 가진다. 보안 프레임워크는 Spring Security.
  - B. A와 같은 서버 세션이지만 **`spring-security-crypto`만** 쓰고 인증 필터는 직접 작성.
  - C. **JWT** 액세스 토큰(상태 없음).
  - D. 불투명 토큰을 DB에 저장하고 `Authorization: Bearer`로 보낸다.
- **추천: A.** 요구가 서버 쪽 통제를 필요로 한다 — 로그아웃 즉시 무효(FR-012), 14일 슬라이딩(FR-007), 기기별 세션(FR-011). 상태 없는 JWT는 즉시 무효가 안 돼서 블랙리스트를 따로 들고 있어야 하므로 결국 서버 상태가 생긴다. 쿠키 + `HttpOnly`는 스크립트로 훔치기 어렵다(D의 `localStorage` 토큰은 XSS에 취약). Spring Security는 설정 비용이 있지만 CSRF, 세션 고정 방어, 헤더 처리를 검증된 코드로 받는다. B는 의존성이 작지만 보안 핵심 코드를 직접 쓰게 된다.
- **새 의존성 이유 (한 줄)**: Spring Security — 비밀번호 해시와 인증 필터·CSRF 방어를 검증된 구현으로 쓰기 위해.
- **설명 체크**: 로그아웃을 즉시 무효로 만들려면 JWT가 왜 서버 상태를 필요로 하게 되는가?

### 2. 비밀번호 해시 — 상태: 확정 (추천대로, 2026-10-26)

- **후보**: A. BCrypt(비용 10~12) / B. Argon2id / C. PBKDF2.
- **추천: A.** Spring Security 기본이고 검증이 가장 많다. 비용은 로그인 응답 1초 목표(SC-010)가 지켜지는 값으로 정하고 측정해 기록한다. 72바이트 제한은 입력 최대 길이(UTF-8 바이트 기준)로 막는다(spec 보완 제안 1). 해시는 인증 단계(`POST /verify`)에서 비밀번호를 받을 때 한 번 만든다(신청 단계에는 비밀번호가 없다, 결정 13). Argon2id가 더 현대적이지만 메모리 비용을 튜닝해야 하고 이 규모에서 이득이 작다.
- **설명 체크**: 비밀번호를 SHA-256 한 번으로 저장하면 안 되는 이유는?

### 3. 인증 토큰 — 상태: 확정 (추천대로, 2026-10-26)

- **후보**: A. 무작위 32바이트(URL-safe) 토큰, DB에는 **SHA-256 해시만** 저장, 24시간 만료·1회 사용 / B. 서명된 토큰(상태 없음) / C. 6자리 코드를 사용자가 입력.
- **추천: A.** 한 번만 쓰고(FR-004) 재발송하면 이전 것이 무효(FR-005)여야 해서 저장이 필요하다. DB가 유출돼도 해시만 있어 링크를 만들 수 없다. 확인은 화면의 `POST`(`/api/auth/verify`)로 한다(spec 보완 제안 3). C는 무차별 대입 방어와 입력 UX를 따로 설계해야 한다.
- **설명 체크**: 메일 링크를 `GET`으로 직접 확인하게 하면 어떤 일이 생기고 `POST`가 왜 이를 막는가?

### 4. 인증 전 가입 신청의 저장 위치 — 상태: 확정 (추천대로, 2026-10-26)

- **후보**: A. 별도 테이블 `pending_signup`에 두고 인증 시 `member`를 만든다 / B. `member`에 `verified_at`이 NULL인 행으로 둔다.
- **추천: A.** `member`에는 인증을 마친 회원만 있어서 `email`·`display_name`의 `UNIQUE`가 단순하다. B는 "인증 전에는 이름·이메일을 점유하지 않는다"(spec)를 지키려면 부분 유일 인덱스가 필요한데 MySQL에는 없다(생성 컬럼 등 우회가 필요). `pending_signup`에는 이메일 키·토큰 해시·만료·한도 컬럼만 있다(이름·비밀번호·동의는 받지 않으므로 컬럼 없음, 결정 13). 같은 이메일로 재제출하면 토큰과 한도만 갱신한다(FR-006).
- **설명 체크**: 같은 이름으로 두 사람이 인증을 마치려 할 때 `UNIQUE`가 어느 시점에 어디서 충돌하는가? (이름은 신청이 아니라 `POST /verify`의 `member` INSERT에서 정해진다.)

### 5. 메일 발송 수단 — 상태: 확정 (추천대로, 2026-10-26)

- **후보**: A. `spring-boot-starter-mail` + SMTP(학교 또는 외부 SMTP 계정) / B. 외부 메일 API(SendGrid, Resend 등) / C. 개발 단계는 `LoggingMailSender`로 기록만 하고 운영에서 A.
- **추천: C(= A + 로깅 구현).** `MailSender` 인터페이스에 두 구현(`SmtpMailSender`, `LoggingMailSender`)을 두고 프로파일로 고른다. 개발·테스트에서 실제 메일이 나가지 않고, 테스트는 발송 내용을 캡처한다. 발송은 요청과 분리된 비동기로 하고(`@Async`, 007과 같은 실행기 패턴), 실패는 사용자가 재발송으로 복구한다(FR-005, 엣지 케이스).
- **새 의존성 이유 (한 줄)**: `spring-boot-starter-mail` — SMTP로 인증 메일을 보내는 표준 구현을 쓰기 위해.
- **준비물(사용자)**: 발송 계정(SMTP 호스트·계정·앱 비밀번호)을 환경 변수로 줄 것. 학교 메일 서버가 외부 발송 메일을 스팸 처리할 수 있어 실제 수신 확인이 필요하다(확인 못 함).
- **설명 체크**: 메일 발송을 요청 처리와 같은 스레드에서 하면 SC-002와 가입 신청 응답에 어떤 영향이 있는가?

### 6. 메일 발송 한도(1분 간격, 24시간 5회) 구현 — 상태: 확정 (추천대로, 2026-10-26)

### 7. 로그인 실패 잠금 — 상태: 확정 (추천대로, 2026-10-26)

- **후보**: A. `login_attempt(email_key, failed_count, locked_until)`에 **이메일 키**로 센다(없는 계정도 동일) / B. `member` 컬럼에 센다(없는 계정은 못 셈).
- **추천: A.** B는 존재하지 않는 이메일에는 잠금이 걸리지 않아 "잠금 안내가 나오면 계정이 있다"는 단서가 된다(FR-010 위반). A는 어떤 이메일이든 5번 틀리면 같은 잠금 안내가 나온다. 갱신은 조건부 `UPDATE`(`failed_count = failed_count + 1`, 5번째에 `locked_until` 설정)로 동시 시도에도 정확하다. 존재하지 않는 계정의 로그인도 더미 해시와 비교해 응답 시간 차이를 줄인다.
- **한계**: 남이 일부러 실패를 쌓아 계정을 15분 막을 수 있다(spec clarify에서 수용). 속도 제한이 필요해지면 IP 단위를 더한다.
- **설명 체크**: 잠금을 `member` 컬럼에 두면 왜 계정 존재 여부가 드러나는가?

### 9. 쿠키·세션 상세 — 상태: 확정 (추천대로, 2026-10-26)

- **후보(추천값)**: 세션 id는 무작위 32바이트, DB에는 SHA-256 해시를 저장. 쿠키 속성은 `HttpOnly`, `SameSite=Lax`, 운영(HTTPS)에서 `Secure`. 슬라이딩은 `last_used_at`을 **10분에 한 번만** 갱신해 읽기 요청마다 쓰기가 생기는 것을 막는다. 만료는 `last_used_at + 14일`. 만료 세션은 정리 작업이 지운다.
- **전제**: 프론트와 API가 같은 출처(리버스 프록시)여야 `SameSite=Lax` 쿠키가 쓰인다. 배포는 4단계에서 정한다.
- **설명 체크**: 슬라이딩 갱신을 요청마다 하면 어떤 비용이 생기고, 10분 간격으로 줄이면 무엇을 포기하는가?

### 10. 인증 필터와 테스트 인증 — 상태: 확정 (추천대로, 2026-10-26)

- **후보**: A. `AuthFilter`가 쿠키 → 세션 → 회원을 해석해 컨트롤러에 `CurrentMember`로 주입하고, `X-Member-Id`는 무시. 테스트는 `IntegrationTestBase.as(memberId)`가 세션 행을 직접 삽입하고 쿠키를 붙인다 / B. 테스트 프로파일에서만 헤더 우회를 남긴다.
- **추천: A.** FR-014는 어떤 환경에서도 헤더가 인증하지 않아야 한다고 한다. B는 테스트와 운영이 달라져 인증 우회 코드가 남는다. 전환을 쉽게 하려면 001 구현 때부터 모든 테스트가 `as(memberId)` 헬퍼로 인증하게 한다(지금은 헤더를 붙이고 002에서 쿠키로 바꾼다).
- **영향 범위(교차)**: 001~007의 모든 IT. 001 tasks의 `IntegrationTestBase` 태스크에 `as(memberId)`를 처음부터 넣는 것을 권장.
- **설명 체크**: 테스트 전용 우회가 운영 보안에 어떤 위험이 되는가?

### 11. 로그인 후 복귀 — 상태: 확정 (추천대로, 2026-10-26)

### 12. 개인정보 동의 기록과 이름 비교 — 상태: 확정 (추천대로, 2026-10-26)

- **후보**: 동의: A. `member.consent_at` + `consent_version`(안내문 버전 문자열, 인증 화면에서 동의하는 시점에 기록) / B. 시각만. 이름 유일성: C. `UNIQUE (display_name)`에 기본 콜레이션(`utf8mb4_0900_ai_ci`, 대소문자·악센트 무시)에 맡김 / D. 정규화 키 컬럼 `display_name_key`(소문자·공백 정리)에 `UNIQUE`.

### 13. 가입 입력을 받는 시점 (변경 B2) — 상태: 확정 (사용자 결정 "안 2", 2026-10-28)

- **문제**: 신청 때 비밀번호를 받으면, 공격자가 피해자의 학교 이메일로 자기 비밀번호를 넣어 먼저 신청해 둘 수 있다. 피해자가 인증 링크를 누르는 순간 공격자가 아는 비밀번호의 계정이 만들어진다(계정 선점, pre-hijacking). 이전 안 B(재제출은 처음 이름·비밀번호 유지)는 덮어쓰기만 막을 뿐 이 선점은 막지 못한다.
- **후보**: A. 신청에서 모두 받는다(이전 설계) / B. 안 B / **C(안 2). 신청은 이메일만, 이름·비밀번호·동의는 인증 단계에서 링크를 누른 사람이 정한다.**
- **결정: C.** 메일함을 가진 사람만 비밀번호를 정할 수 있다. 부수 효과로 재제출 규칙이 단순해지고(토큰·한도만 갱신) 안 B의 '유지' 로직과 `pending_signup`의 이름·비밀번호·동의 컬럼이 사라진다.
- **`POST /verify` 처리 순서**: 토큰 조회(400 INVALID_TOKEN / 409 TOKEN_USED / 410 TOKEN_EXPIRED) → 본문 검증(400 `errors[]`, **토큰 소진 안 함**) → `used_at` 조건부 `UPDATE` 선점 → `member` INSERT → 이름 충돌(409 `DISPLAY_NAME_TAKEN`)·이메일 충돌(409 `ALREADY_REGISTERED`)이면 같은 트랜잭션 롤백으로 `used_at`도 되돌아가 토큰이 유효한 채 남는다 → 성공 200 + `Set-Cookie`.
- **영향**: 비밀번호가 `verify` 요청에 실리므로 로그·오류·응답 어디에도 새지 않아야 하는 범위가 `verify`로 확대된다(PrivacyIT). 검증 오류에서 토큰을 소진하지 않으므로 사용자가 고쳐서 다시 제출할 수 있다. 메일 스캐너가 링크를 `GET`으로 열어도 아무것도 소진되지 않는다(결정 3 유지).
- **설명 체크**: 신청 때 비밀번호를 받으면 어떤 순서로 계정이 선점되고, 인증 때 받으면 왜 그 길이 막히는가?
