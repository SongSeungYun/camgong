# Implementation Plan: 끝난 공구 기록의 보관 기간

**Branch**: `012-record-retention` | **Date**: 2026-11-22 | **Spec**: [spec.md](spec.md)

## Summary

공구가 끝나는 순간을 `group_buy.ended_at`에 남기고, 하루 한 번 정리 작업이 `ended_at`이 1년 지난 공구를 참여 기록·알림과 함께 지운다. 그 뒤 함께한 공구가 없는 탈퇴 회원 행을 지운다.

## Technical Context

Java 21, Spring Boot 4.1.2, MySQL 8.4(Flyway V5, 011의 V4 다음). 알림 30일 정리(`NotificationCleanup`)와 같은 스케줄 작업 모양. 새 외부 의존성 없음.

## Constitution Check

- I. 범위 상한: 처리방침의 보유 기간을 지키기 위한 정리 작업 하나. 사용자 결정(2026-11-22). 통과.
- II. 측정: 성능 주장 없음. 정리가 요청을 막지 않는다는 것(SC-004)은 잠금 범위로 설명하고 통합 테스트로 확인한다.
- III. 설명 가능: 아래 결정마다 대안과 이유. 통과.
- IV. 핵심 로직 테스트: 의무 대상은 아니다. Testcontainers 통합 테스트로 덮는다.

## 결정 (research)

### 1. "끝난 날" — 새 열 `ended_at`
- `group_buy.ended_at DATETIME(6) NULL`. 공구가 COMPLETED·FAILED·CANCELLED로 바뀌는 문장에서 함께 기록한다(004 모집 완료, 005 마감 확정, 001 취소). 끝나지 않은 공구는 NULL.
- 인덱스 `(ended_at)`.
- 대안: `updated_at` → 끝난 뒤에도 이 열을 건드리는 변경이 생기면 보관 기간이 말없이 늘어난다. 지금도 그런 경로가 없다는 것을 계속 보장하기 어렵다. `deadline` → 완료는 마감 전에 일어나고, 취소는 마감과 무관하다. 둘 다 탈락.
- 마이그레이션은 이미 끝난 공구의 `ended_at`을 `updated_at`으로 채운다(운영 데이터는 없지만 로컬·측정 데이터가 있다).

### 2. 정리 순서 — 공구 묶음 단위 트랜잭션
- 하루 한 번(`camgong.retention.cleanup`, 기본 켜짐, 테스트는 끔). 기준은 `now − 365일`(`camgong.retention.ended-for`, 기본 `365d`).
- 한 라운드: `ended_at < 기준`인 공구 id를 100개까지 고른다 → 한 트랜잭션에서 그 공구들의 `notification`(group_buy_id) → `participation` → `group_buy` 순서로 지운다. 공구 하나는 통째로 지워지거나 남는다(FR-006). 더 없을 때까지 라운드를 되풀이한다.
- 잠금: 끝난 공구는 참여·수정·마감이 건드리지 않는다(001 `NOT_MODIFIABLE`, 004는 OPEN만, 005는 OPEN만). 006 체크 토글만 끝난 공구를 잠근다(공구 S → 참여 X). 정리는 같은 순서의 반대(참여 X → 공구 X)라 1년 지난 공구에서 체크와 동시에 돌면 교착할 수 있다. 정리 라운드는 교착(1213)이면 한 번 다시 한다(알림 정리와 같은 처리, 010 T024). 1년 지난 공구에서 체크하는 일은 드물다.
- 대안: 공구 하나씩 트랜잭션 → 트랜잭션이 많아질 뿐 이득이 없다. 한 트랜잭션에 전부 → 오래 잠그고 실패하면 전부 되돌린다. 둘 다 탈락.

### 3. 탈퇴 회원 행
- 공구 정리 뒤 같은 작업에서: `withdrawn_at IS NOT NULL`이고, 그 회원을 개설자로 하는 공구와 그 회원의 참여가 없는 회원 행을 100개씩 지운다.
- 그 회원을 가리키는 다른 행: `login_session`(탈퇴 때 지움, 남았으면 같이 지움), `notification`(탈퇴 때 지움), `create_guard`(탈퇴 때 지움), `password_reset`(011, 탈퇴 때 지움). FK가 있는 것은 먼저 지운다.
- 탈퇴하지 않은 회원은 지우지 않는다(FR-004).
- 장부(010 결정 5-2)와의 관계: 회원 행을 지운 뒤 덤프를 복구하면 그 회원이 되살아나고 장부가 다시 익명화한다. 그 뒤 이 정리가 다시 지운다.

### 4. 화면·API
- 지운 공구는 그냥 없는 공구다. 상세 404, 내 활동·체크표·목록에 없음. 새 오류 코드는 없다.

### 5. 로그
- `retention-cleanup groupBuys=N members=M` INFO. id·이름은 남기지 않는다.

## 검증 (quickstart)

1. 시계를 옮겨 끝난 지 365일 + 1분 된 완료·실패·취소 공구, 364일 된 공구, 마감이 2년 지난 OPEN 공구를 만든다 → 정리 → 첫 셋과 그 참여·알림만 사라짐.
2. 탈퇴 회원 A(남은 공구 없음), B(남은 공구 있음), 탈퇴 안 한 C(남은 공구 없음) → 정리 → A만 사라짐.
3. 1년 지난 공구에 체크 토글과 정리를 동시에 반복 → 500 없음, 정리는 결국 끝남.
