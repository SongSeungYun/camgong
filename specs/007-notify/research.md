# Research: 알림

**모든 결정은 `상태: 사용자 결정 대기`다.** 밤샘 작성이라 사용자에게 물을 수 없었다. 각 결정에 후보와 **추천**, 이유, 설명 체크를 적었고 plan·data-model·contracts·quickstart는 추천안 기준으로 썼다.

## 결정

### 1. 알림을 만드는 시점과 실행 위치 — 상태: 사용자 결정 대기

- **후보**
  - A. 사건 트랜잭션이 **커밋된 뒤**(`AFTER_COMMIT`) 비동기(`@Async`) 리스너가 **새 트랜잭션**으로 알림을 만든다.
  - B. 사건과 **같은 트랜잭션**에서 알림 행을 삽입한다.
  - C. 사건과 같은 트랜잭션에 이벤트 한 줄을 저장(아웃박스)하고 별도 워커가 알림으로 펼친다.
- **추천: A.** 004·005에서 이미 "이벤트는 커밋 후 발행, 유실은 허용된 한계"로 정했다. A는 그 결정과 맞고, 롤백된 변경은 이벤트가 안 나가므로 FR-008이 자연히 지켜지며, 비동기라 수신자가 1,000명이어도 원 요청이 느려지지 않는다(FR-012). B는 유실이 없지만 삽입이 실패하면 원 요청이 실패하고 수신자가 많으면 트랜잭션이 길어져 FR-012를 어긴다. C는 가장 견고하지만 워커·재처리 구조가 필요해 MVP에 과하다.
- **한계 (ponytail)**: 커밋 직후 서버가 멈추면 알림이 한 번도 안 들어갈 수 있다(spec이 허용). 신뢰성이 필요해지면 C로 올린다.
- **설명 체크**: 리스너를 `@Async`로 돌리지 않고 커밋 직후 같은 스레드에서 돌리면 FR-012에 어떤 문제가 생기는가?

### 2. 중복 방지 키 — 상태: 사용자 결정 대기

- **후보**
  - A. 모든 이벤트 record에 `eventId`(UUID, 발행 시 한 번 생성)를 더하고 `UNIQUE (event_id, recipient_id)`.
  - B. 자연 키 `(type, group_buy_id, group_buy_version, recipient_id)`.
- **추천: A.** 같은 이벤트 객체가 두 번 처리돼도 `eventId`가 같아 한 번만 들어간다. B는 수정 사건 사이를 구분하려면 공구의 `version`을 이벤트에 실어야 하는데, `version`은 참여 등 알림과 무관한 쓰기에서도 오르므로 의미가 흐려진다.
- **영향 범위 (교차 변경)**: 001의 `GroupBuyChanged`·`GroupBuyCancelled`·`GroupBuyCompleted`, 005의 `GroupBuyFailed` record에 `eventId`를 추가하고 발행 지점에서 `UUID.randomUUID()`를 넣어야 한다. 구현은 이 변경이 반영된 뒤에 007을 만든다.
- **설명 체크**: 연속으로 두 번 수정했을 때 두 알림이 서로 다른 사건으로 구분되는 이유는? 같은 이벤트를 재처리했을 때 한 번만 들어가는 이유는?

### 3. 대량 생성 방식 — 상태: 사용자 결정 대기

- **후보**: A. `JdbcClient` 배치 `INSERT … ON DUPLICATE KEY UPDATE id = id`(중복은 무시)를 청크(500명)로, 청크가 실패하면 그 청크만 단건 삽입으로 격리 / B. JPA `saveAll` / C. 단건 루프.
- **추천: A.** JPA는 `IDENTITY` 키에서 JDBC 배치가 꺼져 1,000건이 1,000번 왕복이 된다. 청크 실패를 단건으로 격리하면 한 사람의 실패가 나머지를 막지 않는다(FR-009).
- **주의**: 중복 무시의 판정은 영향 행 수에 기대지 않는다(`useAffectedRows` 의존을 피하려고 `id = id`로 변경 없는 갱신을 쓰고, 개수는 세지 않는다).
- **설명 체크**: 청크 하나가 실패했을 때 그 청크를 단건으로 다시 넣는 것이 왜 중복을 만들지 않는가?

### 4. 실패 재시도 — 상태: 사용자 결정 대기

- **후보**: A. 프로세스 안에서 최대 3회, 지수 대기(예: 1초, 4초, 16초) 후 로그를 남기고 포기 / B. DB에 재시도 대기열을 저장해 워커가 재처리.
- **추천: A.** spec은 "다시 시도되어야" 한다고만 했고 서버가 멈추면 이벤트 자체가 유실될 수 있다는 한계를 이미 받아들였다. 재시도 안전성은 결정 2의 `UNIQUE`가 보장한다. B는 결정 1의 C와 함께 갈 때 의미가 있다.
- **설명 체크**: 재시도가 같은 알림을 두 번 만들지 않는 이유는?

### 5. 읽지 않은 개수 — 상태: 사용자 결정 대기

- **후보**: A. `COUNT(*) WHERE recipient_id = ? AND read_at IS NULL`(인덱스 `(recipient_id, read_at)`) / B. 회원 행에 카운터 컬럼을 두고 증감.
- **추천: A.** 보관이 30일이라 회원당 행이 적고 인덱스로 충분하다. 카운터는 알림 생성·읽음·정리마다 동기화해야 해서 어긋날 위험이 크다.
- **설명 체크**: 카운터 컬럼 방식이 어긋나기 쉬운 지점은 어디인가?

### 6. 알림 목록 페이지네이션 — 상태: 사용자 결정 대기

- **후보**: A. 003과 같은 키셋(`id DESC`, 불투명 커서, `size + 1`, 전체 건수 없음) / B. 오프셋.
- **추천: A.** 003과 방식이 같아 프론트가 한 가지만 구현한다. 알림은 새로 쌓이므로 오프셋은 이어 볼 때 중복이 생긴다.

### 7. 알림 내용 저장 — 상태: 사용자 결정 대기

- **후보**: A. 알림 행에 `group_buy_title`(스냅샷)과 `changed_fields`(쉼표 구분 텍스트)를 저장 / B. 공구를 조인해 렌더링 시점에 제목을 읽음.
- **추천: A.** 취소된 공구는 읽을 수 없어 제목을 알림이 직접 가져야 하고(FR-003), 공구 제목이 나중에 수정돼도 알림은 사건 시점의 내용을 보여준다. 조인이 없으니 목록 쿼리도 단순해 N+1 걱정이 없다.

### 8. 정리 작업 — 상태: 사용자 결정 대기

- **후보**: A. 하루에 한 번 `@Scheduled`, `DELETE … WHERE created_at < :cutoff LIMIT 1000`을 반복 / B. 읽는 시점에 지연 삭제.
- **추천: A.** 005 스케줄러와 같은 패턴(`fixedDelay`, 설정으로 끄기)을 쓴다. `DELETE … LIMIT`은 여러 인스턴스가 동시에 돌려도 서로 다른 행을 지우거나 이미 지워진 행을 건너뛰어 안전하다.
- **설명 체크**: 정리 작업이 두 인스턴스에서 동시에 돌아도 문제가 없는 이유는?

### 9. 패키지 위치 — 상태: 사용자 결정 대기

- **후보**: A. 최상위 `notification` / B. `groupbuy.notify`.
- **추천: A.** 알림은 공구 애그리거트의 일부가 아니고 이후 다른 도메인의 사건도 받을 수 있다(architecture 5절의 `notification/`). 의존은 `notification → groupbuy` 한 방향이다.

### 10. 비동기 실행기 — 상태: 사용자 결정 대기

- **후보**: A. 알림 전용 작은 스레드 풀(예: 코어 2, 최대 4)과 큐 상한(예: 1,000), 가득 차면 거부 후 WARN 로그 / B. 가득 차면 호출 스레드가 직접 실행(`CallerRuns`) / C. 기본 실행기.
- **추천: A.** `CallerRuns`는 원 요청을 느리게 만들어 FR-012를 어긴다. 거부된 알림은 유실로 취급(허용된 한계)하고 로그로 남긴다. 기본 실행기는 요청마다 스레드를 만들 수 있어 위험하다.
