# Plan: 서버 밖 백업 (운영자 맥으로 내려받기)

**Date**: 2026-11-26 | **배경**: 사용자 선택 "열기 전, 맥으로 받기"(2026-11-26).
- 지금은 덤프(`deploy/backup.sh`, 매일 04:00)와 탈퇴 장부가 서버 디스크에만 있다. 서버째 잃으면 둘 다 사라진다(`docs/deploy-checklist.md` 7.1-5·6).
- 새 위탁 업체나 비용 없이, 운영자 맥이 매일 내려받아 사본을 둔다.

## Constitution Check

- I. 범위 상한: 백업 사본 하나다. 앱 동작·스키마 변경 없음. 통과.
- III. 설명 가능: 결정마다 이유를 적는다.
- IV. 테스트: 지우는 규칙(아래 결정 4)은 데이터를 잃게 할 수 있는 분기라 실행 가능한 확인을 하나 남긴다.

## 결정

### 1. 맥이 당겨 온다 (서버가 밀지 않는다)
- 서버에는 맥에 들어갈 자격 증명이 없다. 서버가 털려도 맥 사본은 지울 수 없다.
- 맥은 launchd로 매일 한 번 돈다(서버 백업 뒤, 예: 05:00). 맥이 자고 있으면 깨어날 때 돈다. 꺼져 있던 날은 건너뛰고, 다음 성공 때 서버에 남은 덤프를 모두 받는다.

### 2. 전용 SSH 키, 서버에서는 읽기 전용
- 사람이 쓰는 키(암호 있음)와 따로, 암호 없는 전용 키를 맥에 만든다(무인 실행).
- 서버 `authorized_keys`에서 그 키는 백업 디렉터리 읽기만 하게 묶는다(`restrict`와 `command="rrsync -ro <백업 디렉터리>"` 같은 방식). 셸, 포트 포워딩, 쓰기는 안 된다.
- Ubuntu 26.04에서 `rrsync`가 어디 있는지는 확인한다(확인 못 함).
- 키를 잃어도 할 수 있는 일은 백업 읽기뿐이다. 그 백업은 원래 이 맥에 있는 것과 같다.

### 3. 장부도 같이
- `backup.sh`가 덤프를 마친 뒤 탈퇴 장부를 백업 디렉터리에 복사한다. 하나의 파일을 매일 덮어쓴다.
- 복구 때는 가장 새 장부가 필요하다. 덤프 시점 뒤의 탈퇴를 다시 적용해야 하기 때문이다(010 결정 5-2).
- 장부 파일은 uid 10001이 만든다. 백업을 도는 계정이 읽을 수 있는지 확인한다.

### 4. 맥의 보관 기간: 서버와 같은 규칙, 단 서버를 따라 지우지 않는다
- 덤프는 `backup.sh`와 같은 기준으로 6일(분 단위)이 지나면 지운다. 장부는 매번 덮어쓴다.
- **이번 실행에서 새 덤프를 받았을 때만** 지운다.
  - 서버가 사라져 접속이 안 되면 맥 사본은 남는다.
  - 서버 디렉터리가 비어 있거나 덤프가 며칠 실패해도 맥 사본은 남는다.
  - 그동안은 7일을 넘길 수 있다. 서버 쪽 규칙과 같고, 알림(결정 5)으로 알아챈다.
- `rsync --delete`처럼 서버의 상태를 거울처럼 따라 하지 않는다. 서버에서 지워지면 맥에서도 지워지기 때문이다.

### 5. 실패 알림
- 서버 백업과 같은 방식으로 healthchecks.io에 확인을 하나 더 만든다(주기 1일).
- 맥 스크립트는 끝까지 성공하면 그 주소를 부르고, 실패하면 `/fail`을 부른다.
- 주소는 맥의 설정 파일에만 둔다(저장소에 넣지 않는다).

### 6. 맥 쪽 보관 위치
- 홈 아래 전용 디렉터리(예: `~/camgong-offsite`, 권한 700)에 둔다. iCloud로 동기화되는 Desktop·Documents 아래는 쓰지 않는다.
- **Time Machine에서 뺀다**(`tmutil addexclusion`). 그러지 않으면 지운 덤프가 Time Machine에 남아 7일 규칙이 깨진다.
- FileVault(디스크 암호화)를 켠다(처리방침 8 "운영자의 컴퓨터(디스크 암호화)").

## 검증

1. 지우는 규칙(결정 4): 원격 대신 로컬 디렉터리를 원천으로 두고 맥 스크립트를 돌린다(rsync는 로컬 경로도 받는다). 다음 세 경우를 확인한다.
   - 새 덤프가 왔고 7일 넘은 사본이 있다 → 그 사본만 지움.
   - 원천이 비었다 → 아무것도 안 지움.
   - 원천에 접속이 안 된다(없는 경로) → 아무것도 안 지움, 실패 알림.
2. 실제 서버에서의 키 제한(읽기 전용, 셸 불가)과 launchd 실행은 사용자가 체크리스트대로 한 번 확인한다.
3. 맥 사본으로 로컬 MySQL에 복구해 본다(행 수 확인).
