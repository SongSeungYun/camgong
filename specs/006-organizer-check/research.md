# Research: 개설자용 참여자·입금·수령 체크

**모든 결정은 `상태: 사용자 결정 대기`다.** 밤샘 작성이라 사용자에게 물을 수 없었다. 각 결정에 후보와 **추천**, 이유, 설명 체크를 적었고 plan·data-model·contracts·quickstart는 추천안 기준으로 썼다. 사용자가 다른 후보를 고르면 해당 문서를 같이 고친다.

## 결정

### 1. API 형태 — 상태: 사용자 결정 대기

- **후보**
  - A. 필드별 `PUT`: `PUT …/participations/{memberId}/payment`, `PUT …/receipt`, 본문 `{ "confirmed": true|false }` (목표 상태 지정).
  - B. 한 번에 `PUT …/participations/{memberId}/checks` 본문 `{ "paid": bool, "received": bool }`.
  - C. 토글 `POST …/payment/toggle`.
- **추천: A.** 입금과 수령은 독립이라(clarify) 한 요청이 다른 필드를 덮어쓸 위험이 없는 쪽이 낫다. B는 오래된 화면 값이 다른 필드를 되돌리는 갱신 손실이 생긴다. C는 재시도·더블 클릭에서 결과가 뒤집혀 FR-005를 어긴다.
- **설명 체크**: 토글이 아니라 목표 상태를 지정하는 방식이 더블 클릭에서 왜 안전한가?

### 2. 쓰기와 동시성 — 상태: 사용자 결정 대기

- **후보**
  - A. `participation` 한 행에 대한 **조건부 `UPDATE` 한 문장**. 지정: `SET paid_at = COALESCE(paid_at, :now) WHERE group_buy_id = :g AND member_id = :m`, 되돌리기: `SET paid_at = NULL`.
  - B. 공구 행 `FOR UPDATE`로 직렬화한 뒤 갱신.
  - C. 참여 행에 `version`을 두고 낙관적 갱신.
- **추천: A.** `COMPLETED`는 종료 상태라 공구 행이 이후 바뀌지 않는다(상태·개설자 불변). 그래서 공구 락이 필요 없고, 한 문장 `UPDATE`가 행 단위로 원자적이다. `COALESCE`로 이미 지정된 시각을 덮어쓰지 않아 멱등이다. 마지막으로 처리된 요청이 최종이다(SC-007).
- **전제**: 접근 규칙(개설자, 모집 완료)은 같은 트랜잭션 안에서 읽어 검사한다. 읽은 뒤 상태가 바뀌지 않는다는 점이 전제다(종료 상태).
- **설명 체크**: 공구 행 락을 잡지 않아도 되는 이유는 무엇이고, 004의 참여에서는 왜 잡았는가?

### 3. 저장 형태 — 상태: 사용자 결정 대기

- **후보**: A. `paid_at`, `received_at` 컬럼(NULL = 확인 전) / B. `paid`, `received` 불리언 + 시각 컬럼 / C. 별도 `check_log` 테이블(이력).
- **추천: A.** 불리언과 시각을 한 컬럼으로 표현해 불일치가 없다. 이력(C)은 MVP 범위 밖이다(spec Assumptions).
- **설명 체크**: 시각 컬럼 하나가 불리언 + 시각 두 컬럼보다 안전한 이유는?

### 4. 체크표 조회 쿼리 — 상태: 사용자 결정 대기

- **후보**: A. 003의 개설자용 명단 쿼리(`participation join fetch member`)를 재사용하되 개설자 행 제외 + 확인 시각 포함 / B. 체크표 전용 DTO 프로젝션 쿼리.
- **추천: A.** 같은 참여자 정보를 읽으므로 쿼리를 하나로 맞추면 N+1 점검 대상이 하나다. 003이 N+1을 푼 최종 구현(fetch join / batch / 프로젝션)을 그대로 쓴다. 쿼리 수 상한은 개설자 상세와 같은 방식으로 회귀 테스트한다.
- **설명 체크**: 체크표가 003 명단과 다른 쿼리를 쓰면 어떤 위험이 있는가?

### 5. 이름 검색과 필터 위치 — 상태: 사용자 결정 대기

- **후보**: A. 필터(`all|unpaid|unreceived`)는 서버 쿼리 파라미터, 이름 검색은 클라이언트에서 / B. 둘 다 서버(`q` 파라미터) / C. 둘 다 클라이언트.
- **추천: A.** 체크표는 한 번에 전체(최대 약 1,000행)를 내려주므로 이름 검색은 클라이언트가 충분하다. 필터는 요약 숫자가 전체 기준이어야 해서(spec) 서버가 전체 요약과 필터된 목록을 같이 주는 편이 정확하다.
- **설명 체크**: 요약 숫자는 필터와 무관하게 전체 기준인데, 필터를 서버에서 하면 요약은 어떻게 계산하는가?

### 6. 참여자 본인 상태의 노출 — 상태: 사용자 결정 대기

- **후보**: A. 003 상세의 `myParticipation`에 `paidConfirmedAt`, `receivedConfirmedAt`(nullable) 추가 / B. 불리언 `paid`, `received`만 / C. 별도 엔드포인트.
- **추천: A.** 003 계약의 필드 추가만으로 끝나고 화면이 확인 시각까지 보여줄 수 있다. 다른 참여자의 상태는 어디에도 내려가지 않는다(FR-007).
- **영향**: 003 contracts(`browse-api.md`)와 `GroupBuyDetail` 수정이 필요하다. 003 구현 이후에 반영한다.

### 7. 개설자 행 제외 방식 — 상태: 사용자 결정 대기

- **후보**: A. 쿼리에서 `p.member_id <> g.organizer_id`로 제외 / B. 서비스에서 걸러냄.
- **추천: A.** 요약의 분모(전체 인원)와 목록이 같은 조건을 쓰게 되어 어긋나지 않는다. 체크 요청에서 개설자 본인 지정은 400(`INVALID_TARGET`)로 거부한다.

### 8. 오류 코드 — 상태: 사용자 결정 대기 ([cross-check-2](../../docs/cross-check-2.md) Y3 연계)

- **후보**: A. 이 기능 전용 코드 `ORGANIZER_ONLY`(403), `NOT_CHECKABLE`(409, 모집 완료 아님) / B. 기존 `NOT_MODIFIABLE`·`ORGANIZER_NOT_ALLOWED` 재사용.
- **추천: A**, 단 `docs/architecture.md` 6.1의 오류 코드 표로 모아 이름을 정리하면서 확정한다. B는 의미가 달라(`ORGANIZER_NOT_ALLOWED`는 "개설자는 못 함", 여기는 "개설자만 가능") 혼동된다.
