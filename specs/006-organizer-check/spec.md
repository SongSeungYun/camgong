# Feature Specification: 개설자용 참여자·입금·수령 체크

**Feature Branch**: `006-organizer-check`

**Created**: 2026-10-26

**Status**: Draft

**Input**: User description: "개설자용 참여자·입금·수령 체크 (기능 지도 006, 화면 S09)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 참여자별 입금을 체크하기 (Priority: P1)

모집이 끝난 공구의 개설자가 참여자 체크표를 열어, 누가 얼마를 내야 하는지 보고, 입금을 받을 때마다 그 사람 옆에 입금 확인을 표시한다. 잘못 표시했으면 되돌린다.
돈은 서비스 밖(오픈채팅에서 안내받은 방법)에서 오가고, 서비스는 개설자의 기록만 맡는다. 지금은 입금 확인이 DM에 흩어져 누가 냈는지 헷갈리는데, 이 체크표가 한곳에 모아준다.

**Why this priority**: 공구가 성공한 뒤 개설자가 가장 먼저, 가장 자주 하는 일이 "누가 입금했나"를 확인하는 것이다. MVP에 이 확인이 들어 있다.

**Independent Test**: 모집이 완료된 공구의 개설자가 체크표에서 참여자의 이름·수량·금액을 확인하고, 한 명의 입금을 체크했다가 되돌려 요약과 상태가 맞게 바뀌는지, 개설자가 아닌 사람은 체크표를 못 보는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 모집이 완료된 공구(개설자 수량 9, 참여자 6개와 9개)와 그 개설자가 있고, **When** 체크표를 열면, **Then** 개설자를 제외한 참여자 2명의 이름, 수량, 내야 할 금액(개당 가격 × 수량), 입금·수령 상태가 보이고, 입금 완료 0/2명, 수령 완료 0/2명이라는 요약이 보인다.
2. **Given** 체크표에서, **When** 개설자가 한 참여자의 입금을 체크하면, **Then** 그 참여자의 입금 상태가 확인됨으로 바뀌고 확인된 시각이 기록되며 요약이 입금 완료 1/2명으로 바뀐다.
3. **Given** 입금이 체크된 참여자가 있고, **When** 개설자가 체크를 되돌리면, **Then** 입금 상태가 확인 전으로 돌아가고 요약도 함께 돌아간다.
4. **Given** 개설자가 아닌 사람(참여자 포함)이 있고, **When** 같은 공구의 체크표를 열려 하면, **Then** 거부된다.
5. **Given** 모집 중이거나, 모집 실패, 마감됨(확정 대기), 취소된 공구가 있고, **When** 개설자가 체크표를 열거나 체크하려 하면, **Then** 모집 완료 후에만 쓸 수 있다고 안내되거나(취소된 공구는 찾을 수 없다고) 거부된다.
6. **Given** 같은 참여자의 입금 체크를 두 번 요청했고, **When** 둘 다 처리되면, **Then** 결과는 한 번 체크한 것과 같다(체크는 켜기·끄기가 아니라 상태를 지정하는 동작이다).

### User Story 2 - 참여자별 수령을 체크하기 (Priority: P2)

물건이 도착해 나눠주면서, 개설자가 참여자별로 수령 확인을 표시한다. 수령 체크는 입금 체크와 따로 움직인다.

**Why this priority**: 입금 확인(US1) 다음으로 필요한 기록이다. 물건을 먼저 받아가고 나중에 입금하는 경우 등이 있어 둘은 독립이다.

**Independent Test**: 입금 여부와 상관없이 참여자의 수령을 체크하고 되돌리며, 요약과 상태가 맞게 바뀌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 입금이 아직 체크되지 않은 참여자가 있고, **When** 개설자가 그 참여자의 수령을 체크하면, **Then** 수령 상태가 확인됨으로 바뀌고 확인된 시각이 기록되며 요약의 수령 완료 인원이 늘어난다.
2. **Given** 수령이 체크된 참여자가 있고, **When** 개설자가 되돌리면, **Then** 수령 상태가 확인 전으로 돌아간다. 입금 상태에는 영향이 없다.
3. **Given** 모든 참여자의 입금과 수령이 체크되었고, **When** 체크표를 열면, **Then** 요약이 입금 완료와 수령 완료 모두 전체 인원으로 보인다.

### User Story 3 - 참여자가 내 입금·수령 확인 상태 보기 (Priority: P2)

참여자가 공구 상세에서 개설자가 내 입금과 수령을 확인했는지 본다. 참여자가 직접 체크하는 것은 아니다. "입금했는데 확인이 됐나?"를 개설자에게 묻지 않아도 된다.

**Why this priority**: 개설자와 참여자 사이의 DM 확인을 줄이는 것이 이 기능의 목적이다. 개설자 쪽(US1, US2)이 먼저다.

**Independent Test**: 개설자가 한 참여자의 입금을 체크한 뒤, 그 참여자와 다른 참여자가 각자 상세를 열어 자기 상태만 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 개설자가 내 입금을 체크했고, **When** 내가 공구 상세를 열면, **Then** 내 입금이 확인되었다는 상태가 보인다.
2. **Given** 개설자가 아직 내 수령을 체크하지 않았고, **When** 내가 상세를 열면, **Then** 수령은 확인 전으로 보인다.
3. **Given** 다른 참여자의 입금이 체크되었고, **When** 내가 상세를 열면, **Then** 다른 참여자의 상태는 보이지 않는다.

---

### Edge Cases

- 참여자가 개설자뿐이면(다른 참여자 없음) 체크표는? → 체크할 참여자가 없다고 안내하고, 요약은 0/0명이다.
- 개설자 본인의 행은? → 체크표에서 제외한다. 개설자는 입금을 받는 쪽이라 입금할 상대가 없다.
- 입금을 해제하면 수령 상태에 영향이 있나? → 없다. 둘은 독립이다.
- 참여자가 아주 많으면(수량 1개씩 1,000명까지 가능)? → 체크표는 한 번에 전체를 보여주며 사용자는 이름을 찾아 체크할 수 있어야 한다(FR-009).
- 체크하는 동안 공구 상태가 바뀌면? → 모집 완료는 종료 상태라 바뀌지 않는다. 취소·수정도 불가이므로 체크표의 참여자는 변하지 않는다.
- 다른 공구의 참여자 번호로 체크를 요청하면? → 그 공구의 참여자가 아니면 찾을 수 없다고 거부된다.
- 같은 참여자에 대한 체크 요청이 동시에 여러 번 오면? → 마지막으로 처리된 결과가 최종이고, 기록이 중복되거나 어긋나지 않는다.
- 체크 후 새로고침하거나 다른 기기에서 열면? → 같은 상태가 보인다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 체크표는 모집이 완료된 공구의 개설자에게만 보여야 한다. 개설자가 아닌 사용자는 거부되고, 모집 완료가 아닌 공구(모집 중, 마감됨(확정 대기), 모집 실패)는 쓸 수 없다고 안내되며, 취소된 공구는 찾을 수 없다. 로그인하지 않은 사용자는 로그인을 요구받는다.
- **FR-002**: 체크표는 개설자를 제외한 참여자별로 이름, 수량, 내야 할 금액(개당 가격 × 수량), 입금 확인 여부와 확인 시각, 수령 확인 여부와 확인 시각을 보여줘야 한다. 같은 화면에 입금 완료 인원/전체 인원, 수령 완료 인원/전체 인원, 확인된 입금 금액 합/받아야 할 금액 합을 요약으로 보여줘야 한다.
- **FR-003**: 개설자는 참여자별로 입금을 확인됨으로 지정하거나 확인 전으로 되돌릴 수 있어야 한다. 지정하면 확인 시각이 기록되고, 되돌리면 확인 시각이 지워진다.
- **FR-004**: 개설자는 참여자별로 수령을 확인됨으로 지정하거나 확인 전으로 되돌릴 수 있어야 한다. 수령 체크는 입금 체크와 독립이며, 입금이 확인되지 않아도 수령을 체크할 수 있다.
- **FR-005**: 체크 요청은 목표 상태를 지정하는 동작이어야 한다. 이미 그 상태인 참여자에게 같은 요청을 반복해도 결과는 같고 확인 시각을 새로 덮어쓰지 않는다. 같은 참여자에 대한 요청이 동시에 와도 상태와 기록이 어긋나지 않아야 한다.
- **FR-006**: 체크 대상은 해당 공구의 개설자가 아닌 참여자로 한정해야 한다. 개설자 본인이나 다른 공구의 참여자, 존재하지 않는 참여자를 지정하면 거부하고 이유를 알려야 한다.
- **FR-007**: 참여자는 자기 입금 확인 여부와 수령 확인 여부를 공구 상세에서 볼 수 있어야 한다. 다른 참여자의 체크 상태는 보이지 않는다(참여자 명단은 개설자에게만 공개, 003 FR-012).
- **FR-008**: 입금·수령 체크는 알림을 발생시키지 않아야 한다. 시스템은 돈이 실제로 오갔는지 검증하지 않으며, 체크는 개설자의 기록일 뿐이다.
- **FR-009**: 체크표는 참여자가 많아도 한 화면에서 전체를 보여주고, 개설자가 이름으로 참여자를 찾을 수 있어야 한다.
- **FR-010**: 모집이 완료된 이후에는 체크를 언제든 지정하거나 되돌릴 수 있어야 한다(기한 없음). 체크 기록은 보존된다.
- **FR-011**: 거부된 요청은 어떤 규칙을 어겼는지 사용자가 알 수 있는 이유를 함께 돌려줘야 한다.

### Key Entities

- **참여(Participation)**: 기존 참여에 입금 확인 시각과 수령 확인 시각을 더한다. 값이 없으면 확인 전이다. 개설자의 참여 기록은 체크 대상이 아니다.
- **공구(GroupBuy)**: 모집 완료 상태일 때만 체크표를 가진다. 개당 가격으로 참여자별 금액을 계산한다.
- **회원(Member)**: 체크표에는 개설자에게만 참여자의 표시 이름이 보인다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 개설자가 체크표에서 한 참여자의 입금 또는 수령을 체크하는 데 한 번의 조작이면 충분하다.
- **SC-002**: 참여자 50명인 공구의 체크표가 95%의 요청에서 1초 이내에 열린다.
- **SC-003**: 개설자 외 사용자에게 체크표나 다른 참여자의 체크 상태가 노출되는 경우가 0건이다.
- **SC-004**: 체크한 상태는 새로고침하거나 다른 기기에서 열어도 100% 같게 보이고, 같은 요청을 반복해도 결과가 100% 같다.
- **SC-005**: 모집 완료가 아닌 공구에서 체크가 성공하는 경우가 0건이다.
- **SC-006**: 참여자 본인이 보는 입금·수령 상태가 개설자가 체크한 상태와 100% 일치한다(다시 불러올 때).
- **SC-007**: 같은 참여자에 대한 체크 요청이 동시에 몰려도 최종 상태가 항상 마지막으로 처리된 요청의 결과와 같고 기록이 중복되는 경우가 0건이다.

## Assumptions

- 결제는 서비스 밖에서 이뤄진다(결제 연동 제외). 입금 방법 안내는 오픈채팅에서 한다. 이 기능은 개설자의 기록만 제공한다.
- 참여자가 "입금했어요"를 서비스에서 알리는 기능은 없다. 알림과 대화는 오픈채팅이나 개인 메시지에서 한다.
- 여러 참여자를 한 번에 체크하는 일괄 체크, 체크 변경 이력(누가 언제 바꿨는지)은 MVP에서 다루지 않는다. 마지막 확인 시각만 남긴다.
- 개설자 본인은 체크 대상에서 제외한다. 개설자의 몫을 판매처에 치르는 일은 서비스 밖이다.
- 모집 완료 후에는 참여·수정·취소가 모두 막혀 있어 체크표의 참여자는 고정이다.
- 003의 공구 상세 중 내 참여 정보에 입금·수령 확인 상태를 더한다(003 contracts 갱신 필요).
- 003 상세의 개설자용 명단과 이 체크표는 같은 참여자 정보를 읽는다. 쿼리를 같은 방식으로 맞춘다(N+1 점검 대상).
- 시간은 앱의 기준 시각으로 기록한다(architecture 6.2).
