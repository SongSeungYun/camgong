# Quickstart: 개설자용 입금·수령 체크 검증

> 초안: 추천안 기준(2026-10-26 확정). 요청·응답은 [contracts/check-api.md](contracts/check-api.md), 규칙은 [data-model.md](data-model.md).

구현 후 이 기능이 end-to-end로 동작하는지 확인하는 시나리오다. 001(개설), 004(참여), 005(마감 확정), 003(상세)이 있으면 API로, 없으면 SQL 시드로 공구와 참여자를 만든다. 시간은 `MutableClock`으로 움직인다.

## 준비

- 001 quickstart의 준비(JDK 21, Docker, `useAffectedRows=true`).
- 회원: 개설자 1, 참여자 2·3, 외부인 4.
- 공구: 총 24, 개설자 수량 9, 참여자 2가 6개·참여자 3이 9개로 채워져 `COMPLETED`, 개당 1,200원.
- 자동 테스트: `./gradlew test`.

## 시나리오

| # | 확인 내용 | 요청 | 기대 결과 | spec |
|---|-----------|------|-----------|------|
| 1 | 체크표 열기 | 개설자가 `GET …/check-sheet` | 200, 참여자 2명(개설자 제외)의 이름·수량·금액(7,200 / 10,800), 입금·수령 상태, `summary` = 입금 0/2, 수령 0/2, 받아야 할 금액 18,000, 확인된 금액 0 | US1-1, FR-002 |
| 2 | 입금 체크 | 개설자가 참여자 2의 `payment`를 `confirmed=true` | 200, `paidConfirmedAt` 기록, 요약 입금 1/2·확인 금액 7,200 | US1-2, FR-003 |
| 3 | 되돌리기 | `confirmed=false` | 200, `paidConfirmedAt=null`, 요약 입금 0/2 | US1-3 |
| 4 | 개설자 아님 | 참여자·외부인이 체크표·PUT | 403 `ORGANIZER_ONLY`. 참여자 2는 자기 상태만 상세에서 | US1-4, SC-003 |
| 5 | 모집 완료가 아님 | 모집 중·마감됨·모집 실패 공구, 취소된 공구 | 409 `NOT_CHECKABLE` / 취소된 공구는 404 | US1-5, SC-005 |
| 6 | 멱등 | 같은 `confirmed=true`를 두 번 | 결과 동일, 확인 시각이 새로 덮이지 않음 | US1-6, FR-005, SC-004 |
| 7 | 수령은 독립 | 입금 미확인 참여자에게 `receipt` `confirmed=true` | 200, 수령 시각 기록, 요약 수령 1/2, 입금은 그대로, 행의 `receivedWithoutPayment=true` | US2-1, FR-004, FR-002 |
| 8 | 수령 되돌리기 | `receipt` `confirmed=false` | 수령만 확인 전으로, 입금 불변 | US2-2 |
| 9 | 전원 완료 | 두 참여자의 입금·수령을 모두 체크 | 요약 입금 2/2·수령 2/2·확인 금액 = 받아야 할 금액 | US2-3 |
| 10 | 참여자 본인 상태 | 입금이 체크된 참여자 2와 미체크 참여자 3이 각자 상세 | 2는 `paidConfirmedAt` 값, 3은 `null`, 서로의 상태는 안 보임 | US3-1·2·3, FR-007, SC-006 |
| 11 | 개설자만 있는 공구 | 참여자 없이 `COMPLETED`(개설자가 총 수량을 채운 경우는 없으므로 SQL 시드) | `rows: []`, `participantCount: 0` | 엣지 |
| 12 | 개설자 본인 지정 | `memberId`=개설자 | 400 (`errors`에 `memberId`) | FR-006 |
| 13 | 다른 공구 참여자 | 이 공구에 참여하지 않은 `memberId` | 404 | FR-006 |
| 14 | 필터 | `filter=unpaid`, `filter=unreceived` | 해당 참여자만 `rows`, `summary`는 전체 기준 그대로 | FR-009 |
| 15 | 잘못된 값 | `filter=x`, 본문 `{}` | 400 | FR-011 |
| 16 | 동시 체크 | 같은 참여자에 `true`/`false`를 동시에 여러 번 | 최종 상태가 마지막으로 처리된 요청과 같고 기록이 어긋나지 않음 | SC-007 |
| 17 | 새로고침 | 체크 후 체크표를 다시 열기·다른 기기에서 열기 | 같은 상태 | SC-004 |
| 18 | 대량 | 참여자 50명 | 체크표 95%가 1초 이내, 쿼리 수가 참여자 수와 무관(상한은 003 개설자 상세와 같은 방식) | SC-002 |
| 19 | 알림 없음 | 체크 요청 | 이벤트가 발행되지 않음 | FR-008 |

## 헌법과의 대응

이 기능에는 헌법 IV 필수 대상이 없다. 시나리오 16(동시 체크)과 5·4(접근 규칙)는 통합 테스트로 덮는다. 쿼리 수 상한(시나리오 18)은 003의 `QueryCountInspector`를 쓴다.
