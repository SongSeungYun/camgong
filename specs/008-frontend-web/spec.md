# Feature Specification: 모바일 우선 웹 화면

**Feature Branch**: `008-frontend-web`

**Created**: 2026-10-26

**Status**: Draft

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 목록에서 공구 찾기 (Priority: P1)

기숙사생이 에브리타임 글의 링크를 휴대폰으로 열면, 로그인하지 않아도 지금 모집 중인 공구가 카드로 보이는 첫 화면(S03)이 나온다.
카드에는 제목, 상품명, 개당 가격, 얼마나 찼는지(확보/총 수량 진행률), 마감까지 남은 시간, 상태 뱃지, 카테고리가 보인다.
정렬(최신, 마감 임박), 상태 필터, 카테고리 6개 필터, 검색(제목·상품명)을 쓸 수 있고 '더 보기'로 끝까지 넘겨 볼 수 있다.

**Why this priority**: 사용자가 가장 먼저 만나는 화면이고 로그인 없이도 가치가 있다. 이 화면만으로 에타 글을 일일이 열어 인원을 세던 일이 사라진다.

**Independent Test**: 로그인하지 않은 휴대폰 화면 크기에서 목록을 열어 카드 내용, 정렬·필터·검색, 더 보기, 빈 목록과 검색 결과 없음 안내가 규칙대로 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 모집 중 공구 3개가 있고, **When** 로그인하지 않은 사용자가 목록을 열면, **Then** 3개가 카드로 보이고 카드마다 제목, 상품명, 개당 가격, 확보/총 수량 진행률, 마감까지 남은 시간, 상태 뱃지, 카테고리가 표시된다.
2. **Given** 목록이 한 페이지보다 많고, **When** 사용자가 '더 보기'를 계속 누르면, **Then** 모든 공구가 한 번씩만 이어서 나오고, 더 없으면 '더 보기'가 사라진다.
3. **Given** 사용자가 카테고리, 상태, 정렬, 검색어를 바꾸고, **When** 결과가 나오면, **Then** 선택한 조건이 화면에 표시되고 그 조건에 맞는 공구만 처음부터 보인다.
4. **Given** 공구가 하나도 없거나 검색 결과가 없고, **When** 목록을 보면, **Then** 두 경우가 서로 다른 안내 문구로 구분되어 보인다.
5. **Given** 마감이 지났지만 확정 전인 공구가 있고, **When** 목록에 보이면, **Then** 서버가 알려준 대로 '마감됨(확정 대기)' 뱃지가 붙는다.

### User Story 2 - 로그인하고 상세 보기, 가입하기 (Priority: P1)

비로그인 사용자가 카드를 누르거나 개설·참여·내 활동을 시도하면 로그인 화면(S02)으로 안내된다.
계정이 없으면 학교 이메일로 가입(S01)하고 메일의 인증 링크를 확인해 가입을 마친다. 로그인을 마치면 항상 메인(목록)으로 돌아간다.
로그인한 회원은 상세 화면(S04)에서 개설자 이름, 구매처 링크, 총·확보·남은 수량, 마감, 상태, 참여 인원 수, 내 참여 수량과 부담 금액을 본다.

**Why this priority**: 목록 다음 단계이고 이후의 모든 행동(개설, 참여)의 전제다. 인증 기능(002)의 화면이다.

**Independent Test**: 비로그인으로 상세를 열려다 로그인 화면으로 가고, 가입·인증·로그인 후 목록으로 돌아오는지, 상세에 역할별(개설자, 참여자, 비참여자) 정보가 맞게 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인하지 않은 사용자가 있고, **When** 목록의 카드를 누르거나 로그인이 필요한 화면 주소를 직접 열면, **Then** 로그인 화면이 나오고, 로그인을 마치면 메인(목록)으로 돌아간다.
2. **Given** 가입 화면에서 이메일, 표시 이름, 비밀번호를 입력해 제출하면, **When** 신청이 접수되면, **Then** '인증 메일을 보냈다'는 안내가 나오고 메일 재발송 버튼이 있다. 재발송이 너무 이르면 잠시 뒤 다시 시도하라고 안내된다.
3. **Given** 메일의 인증 링크를 연 사용자가 있고, **When** 링크가 유효하면, **Then** 가입이 끝나 로그인된 상태가 되어 목록으로 간다. 만료되었거나 이미 쓴 링크면 이유를 안내하고 재발송으로 이어진다.
4. **Given** 로그인에 실패하면, **When** 결과가 나오면, **Then** 정보가 틀렸다고만 안내된다. 연속 실패로 잠긴 경우에는 잠시 뒤 다시 시도하라고 안내된다.
5. **Given** 로그인한 회원이 모집 중 공구의 상세를 열고, **When** 내가 6개를 잡았고 개당 1,200원이면, **Then** 내 참여 수량 6개와 내 부담 금액 7,200원이 보이고, 참여하지 않았다면 '참여 안 함'만 보인다.
6. **Given** 로그인한 회원이 취소된 공구나 없는 공구의 상세를 열려고 하면, **When** 결과가 나오면, **Then** 찾을 수 없다는 안내와 목록으로 가는 길이 보인다.
7. **Given** 로그인한 회원이 로그아웃하면, **When** 완료되면, **Then** 비로그인 상태의 목록으로 가고, 뒤로 가기로 상세 등에 돌아가도 이전 내용이 보이지 않고 로그인을 요구받는다.

### User Story 3 - 공구 열기·수정·취소 (Priority: P2)

로그인한 회원이 개설 화면(S05)에서 제목, 설명, 카테고리, 상품명, 구매처 링크, 개당 가격, 총 수량, 내 수량, 마감, 오픈채팅 링크를 입력해 공구를 연다.
입력 중에 내 부담 금액 미리보기가 보이고, 서버가 거부하면 어느 필드가 왜 틀렸는지 해당 필드 옆에 보인다.
개설자는 상세에서 같은 폼(S06)으로 공구를 수정하거나 취소할 수 있다.

**Why this priority**: 공구가 있어야 목록이 채워지지만, 운영 초기에는 개설이 드물어 P1 다음에 둔다.

**Independent Test**: 개설 폼에서 일부러 틀린 값을 여러 개 넣어 필드별 오류가 정확한 위치에 보이는지, 올바른 값으로 연 뒤 상세로 이동하는지, 수정 폼에 현재 값이 채워지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 개설 폼에서 개당 가격 1,200원, 총 수량 24, 내 수량 9를 입력하면, **When** 입력 중이면, **Then** 내 부담 금액 10,800원이 미리보기로 보인다.
2. **Given** 사용자가 마감을 한국 시각으로 입력하고, **When** 제출하면, **Then** 서버에는 오프셋이 포함된 시각으로 전달되고, 이후 모든 화면에서 한국 시각으로 표시된다.
3. **Given** 서버가 여러 필드에 대해 입력 오류를 돌려주면, **When** 결과가 나오면, **Then** 오류가 해당 필드 옆에 모두 한 번에 표시되고, 필드에 매핑되지 않는 오류는 폼 위에 표시된다. 입력한 값은 지워지지 않는다.
4. **Given** 개설에 성공하면, **When** 완료되면, **Then** 새 공구의 상세 화면으로 이동한다.
5. **Given** 개설자가 수정 화면을 열면, **When** 폼이 나오면, **Then** 현재 값이 채워져 있고, 마감은 연장만, 총 수량은 확보 수량 이상만 입력할 수 있다는 안내가 보인다.
6. **Given** 개설자가 취소를 누르면, **When** 확인을 거치면, **Then** 공구가 사라진 것으로 안내되고 목록으로 돌아간다. 확인 없이 바로 취소되지는 않는다.
7. **Given** 개설자가 아닌 회원이 상세를 보면, **When** 화면이 나오면, **Then** 수정·취소 버튼은 보이지 않는다.

### User Story 4 - 공구에 참여하고 취소하기 (Priority: P2)

로그인한 회원이 상세에서 참여(S07)를 눌러 수량을 입력하고 참여한다. 화면은 남은 수량과 내 부담 금액을 미리 보여주고,
참여할 때 화면에서 확인한 개당 가격을 함께 보낸다. 그 사이 가격이 바뀌었으면 바뀐 가격을 안내하고 다시 확인하게 한다.
이미 참여했다면 수량 변경과 참여 취소를 할 수 있다. 마지막 수량 경쟁에서 밀렸거나 이미 마감된 경우 그 이유를 알려준다.

**Why this priority**: 서비스의 핵심 행동이지만, 목록·상세·로그인이 먼저 있어야 시험할 수 있다.

**Independent Test**: 남은 수량이 적은 공구에서 초과 수량을 넣어 거부 안내를 보고, 가격이 바뀐 공구로 참여해 재확인 안내를 보고, 참여·수량 변경·취소 뒤 상세의 수치가 바뀌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 남은 수량이 15개인 공구, **When** 사용자가 수량을 입력하면, **Then** 남은 수량 이하의 값만 제출할 수 있고 내 부담 금액이 미리보기로 보인다.
2. **Given** 사용자가 화면에서 개당 1,200원을 보고 참여를 제출했는데 그 사이 가격이 1,500원으로 바뀌었다면, **When** 서버가 거부하면, **Then** 바뀐 가격을 안내하고 새 가격 기준 금액을 보여주며 다시 확인해야 제출된다.
3. **Given** 다른 사람이 먼저 수량을 가져가 남은 수량이 부족해졌다면, **When** 서버가 거부하면, **Then** 남은 수량이 부족하다는 안내와 최신 남은 수량이 보인다.
4. **Given** 마감되었거나 모집이 끝난 공구에 참여를 제출하면, **When** 서버가 거부하면, **Then** 이유가 안내되고 상세가 최신 상태로 다시 보인다.
5. **Given** 이미 참여한 회원, **When** 상세를 열면, **Then** 참여하기 대신 수량 변경과 참여 취소가 보인다. 참여 취소는 확인을 거친다.
6. **Given** 같은 제출을 연달아 눌렀거나 네트워크 문제로 다시 보내도, **When** 처리되면, **Then** 화면에서 참여가 한 번만 반영된 것으로 보이고 오류처럼 보이지 않는다.
7. **Given** 수량을 채워 모집 완료가 되면, **When** 참여자가 상세를 다시 보면, **Then** '모집 완료' 뱃지와 오픈채팅 입장 링크가 보인다. 참여하지 않은 회원에게는 링크가 보이지 않는다.

### User Story 5 - 내 활동 보기 (Priority: P3)

로그인한 회원이 내 활동(S08)에서 '내가 연 공구'와 '내가 참여한 공구' 탭을 오가며 상태 뱃지와 함께 본다. 항목을 누르면 상세로 간다.

**Why this priority**: 목록·상세만으로도 공구를 찾을 수 있어 편의 기능에 가깝다.

**Independent Test**: 공구를 열고 다른 공구에 참여한 회원으로 두 탭의 내용과 뱃지, 상세 이동을 확인한다.

**Acceptance Scenarios**:

1. **Given** 내가 2개를 열고 다른 3개에 참여했다면, **When** 내 활동을 열면, **Then** 첫 탭에 2개, 둘째 탭에 5개(내가 연 2개 포함)가 보이고 각각 상태 뱃지가 붙는다.
2. **Given** 항목이 한 페이지보다 많다면, **When** 탭에서 '더 보기'를 누르면, **Then** 목록과 같은 방식으로 이어서 나온다.
3. **Given** 내가 참여한 공구를 개설자가 취소했다면, **When** 내 활동을 열면, **Then** 그 공구는 어느 탭에도 보이지 않는다.

---

### Edge Cases

- 로그인 상태가 만료되거나 다른 기기에서 로그아웃되어 요청이 거부되면? → 입력하던 폼 내용을 잃는다는 안내와 함께 로그인 화면으로 보내고, 로그인 후에는 메인(목록)으로 간다.
- 서버에 연결할 수 없거나 응답이 늦으면? → 화면이 멈추거나 빈 화면이 되지 않고, 다시 시도 버튼이 있는 오류 안내가 나온다. 제출 버튼은 처리 중 비활성화되어 중복 제출을 막는다.
- 서버 오류(5xx)면? → 입력값을 지우지 않고 일반 오류 안내를 보여주며, 서버 내부 정보는 노출하지 않는다.
- 남은 시간이 흐르는 동안 마감이 지나면? → 화면이 스스로 상태를 바꾸지 않고, 다시 불러올 때 서버가 계산한 값을 따른다(실시간 갱신 없음). 남은 시간 표시는 불러온 시점 기준으로 보인다.
- 사용자의 기기 시각이 틀리거나 다른 시간대여도? → 마감 판단은 서버가 하고, 화면은 서버가 준 시각과 상태를 한국 시각으로 표시만 한다.
- 구매처·오픈채팅 링크를 눌러 외부로 나갈 때? → 새 창으로 열고, 서비스 밖 링크임이 보인다.
- 매우 긴 제목·설명이나 많은 참여자 명단이 있어도? → 휴대폰 폭에서 가로 스크롤 없이 줄바꿈되고 레이아웃이 깨지지 않는다.
- 데스크톱 폭의 넓은 화면이면? → 읽을 수 있는 폭으로 제한된 중앙 정렬 화면으로 보이며 깨지지 않는다.
- 서버가 알 수 없는 상태 값이나 필드를 돌려주면? → 화면이 멈추지 않고 알 수 없는 상태로 안전하게 표시한다.
- 목록 필터·검색 조건이 있는 채로 상세에 들어갔다 돌아오면? → 보던 조건과 위치가 가능한 한 유지된다.

## Requirements *(mandatory)*

### Functional Requirements

**공통**

- **FR-001**: 모든 화면은 휴대폰 폭(약 360px)에서 가로 스크롤 없이 쓸 수 있어야 하며, 더 넓은 화면에서도 깨지지 않아야 한다.
- **FR-002**: 비로그인 사용자는 목록(S03)만 볼 수 있어야 한다. 상세, 개설, 수정, 참여, 내 활동은 로그인을 요구하고, 로그인을 마치면 항상 메인(목록)으로 돌아가야 한다. 로그인이 필요한 화면의 주소를 직접 열어도 같다.
- **FR-003**: 서버가 인증 거부를 돌려주면(만료 포함) 어느 화면에서든 로그인 화면으로 안내해야 한다. 로그인 상태가 아니면 개인 정보(내 참여, 내 활동)가 화면에 남아 있어서는 안 된다.
- **FR-004**: 사용자가 입력하고 보는 모든 시각은 한국 시각이어야 하고, 서버와 주고받는 시각은 오프셋이 포함된 형식이어야 한다. 변환은 화면의 책임이다.
- **FR-005**: 서버가 입력 오류를 필드별로 돌려주면, 각 오류를 이름이 같은 폼 필드 옆에 한 번에 모두 표시해야 한다. 어느 필드에도 해당하지 않는 오류는 폼 상단에 표시한다. 오류가 있어도 입력값은 유지되어야 한다.
- **FR-006**: 서버가 돌려주는 오류(401, 403, 404, 409, 422 등)는 사용자가 다음 행동을 알 수 있는 말로 바꿔 보여줘야 하며, 서버의 내부 메시지나 스택을 그대로 노출해서는 안 된다.
- **FR-007**: 데이터를 불러오는 중, 비어 있음, 오류 상태가 모든 데이터 화면에서 서로 구분되어 보여야 한다. 데이터를 바꾸는 제출은 처리 중에 중복 제출되지 않아야 한다.
- **FR-008**: 상태 뱃지는 서버가 계산해 준 표시 상태를 그대로 쓴다(모집 중, 마감됨(확정 대기), 모집 완료, 모집 실패). 화면이 시각으로 상태를 다시 계산하지 않는다. 알 수 없는 상태는 안전하게 일반 표시로 처리한다.
- **FR-009**: 외부 링크(구매처, 오픈채팅)는 새 창으로 열고 서비스 밖 링크임을 알 수 있게 해야 한다. 허용되지 않은 형태의 주소(예: http, 스크립트 주소)는 링크로 만들지 않는다.
- **FR-010**: 서버가 준 사용자 입력 문자열(제목, 설명, 이름 등)은 문자 그대로 보여줘야 하며 화면의 코드로 실행되어서는 안 된다.

**목록 (S03)**

- **FR-011**: 목록은 로그인 없이 보이고 카드마다 제목, 상품명, 개당 가격, 확보/총 수량 진행률, 마감 시각과 남은 시간, 상태 뱃지, 카테고리를 보여줘야 한다.
- **FR-012**: 목록은 최신순(기본)과 마감 임박순 정렬, 표시 상태 필터(기본은 모집 중), 고정 6개 카테고리 필터, 제목·상품명 검색(50자 이하)을 지원해야 하고 서로 함께 쓸 수 있어야 한다. 조건을 바꾸면 처음부터 다시 보여준다.
- **FR-013**: 목록은 '더 보기'로 이어서 불러오고, 다음 페이지가 없으면 더 보기가 없어야 한다. 전체 건수는 보여주지 않는다. 검색어가 비었거나 공백뿐이면 검색하지 않은 것으로 다룬다.
- **FR-014**: 공구가 없는 경우와 검색·필터 결과가 없는 경우를 다른 안내로 보여줘야 한다.
- **FR-015**: 선택한 정렬·필터·검색 조건은 주소에 반영되어, 새로고침하거나 상세에서 돌아와도 유지되고 주소를 공유하면 같은 조건의 목록이 열려야 한다.

**가입·로그인 (S01, S02)**

- **FR-016**: 가입 화면은 이메일, 표시 이름, 비밀번호를 받고, 규칙(이메일 형식, 표시 이름 2~20자, 비밀번호 8자 이상, 학교 이메일 도메인)을 제출 전에 안내하되 최종 판단은 서버 응답을 따른다. 인증 메일 안내와 재발송(간격 제한 안내 포함)을 제공해야 한다.
- **FR-017**: 인증 링크를 연 결과(성공, 만료, 이미 사용)를 구분해서 안내해야 하고, 성공하면 로그인된 상태로 메인(목록)에 가야 한다.
- **FR-018**: 로그인 화면은 실패 시 정보가 틀렸다고만 안내하고 어느 쪽이 틀렸는지 알리지 않아야 한다. 인증 전 계정은 이메일 인증이 필요하다고 안내하고 재발송으로 이어주며, 연속 실패 잠금은 잠시 뒤 다시 시도하라고 안내한다. 로그아웃을 제공해야 한다.
- **FR-019**: 비밀번호는 화면에서 가려져 입력되어야 하고, 어떤 화면·주소·저장 공간에도 원문으로 남아서는 안 된다.

**상세 (S04)**

- **FR-020**: 상세는 제목, 설명, 상품명, 카테고리, 구매처 링크, 개당 가격, 총·확보·남은 수량, 마감 시각, 상태 뱃지, 개설자 이름, 참여 인원 수, 내 참여 수량과 부담 금액(참여한 경우)을 보여줘야 한다.
- **FR-021**: 상세의 버튼은 요청자의 역할과 공구 상태에 따라 노출되어야 한다. 개설자에게는 수정·취소, 개설자가 아닌 회원에게는 참여(참여 전) 또는 수량 변경·참여 취소(참여 후)가 보이고, 모집이 끝났거나 마감된 공구에서는 참여 관련 버튼이 보이지 않는다. 버튼 노출은 편의일 뿐 최종 허용 여부는 서버 응답을 따른다.
- **FR-022**: 오픈채팅 링크는 서버가 내려줄 때만 보여준다. 화면이 스스로 조건을 판단해 숨기거나 보이게 하지 않는다. 참여자 명단도 서버가 내려준 경우(개설자)에만 보여준다.
- **FR-023**: 존재하지 않거나 취소된 공구는 찾을 수 없다는 안내와 목록으로 가는 길을 보여줘야 한다.

**개설·수정·취소 (S05, S06)**

- **FR-024**: 개설 폼은 제목(100자 이하), 설명(선택), 카테고리(필수, 6개 중 하나), 상품명(100자 이하), 구매처 링크(필수, https, 500자 이하), 개당 가격(1~1,000,000원), 총 수량(2~1,000), 내 수량(1 이상 총 수량 미만), 마감(지금부터 30일 이내), 오픈채팅 링크(필수)를 받고 내 부담 금액을 미리 보여줘야 한다. 이 범위는 안내용이며 최종 판단은 서버 응답을 따른다.
- **FR-025**: 수정 폼은 현재 값이 채워진 같은 폼이며, 마감은 연장만 가능하고 총 수량은 확보 수량 이상이어야 한다는 안내를 보여줘야 한다. 수정·취소가 성공하면 상세 또는 목록으로 이동한다.
- **FR-026**: 공구 취소와 참여 취소처럼 되돌릴 수 없는 행동은 확인을 거친 뒤에만 실행해야 한다.

**참여 (S07)**

- **FR-027**: 참여 화면은 남은 수량, 개당 가격, 수량 입력, 내 부담 금액 미리보기를 보여주고, 제출할 때 화면에서 확인한 개당 가격을 함께 보내야 한다. 가격이 바뀌어 거부되면 바뀐 가격을 안내하고 사용자가 다시 확인해야만 제출되어야 한다.
- **FR-028**: 참여가 거부되는 이유(수량 부족, 마감, 이미 끝난 모집, 가격 변경)는 각각 구분된 안내로 보여주고, 안내와 함께 최신 상세 내용을 다시 불러와 보여줘야 한다. 마감·완료·실패는 거부 응답의 `reason`(`DEADLINE_PASSED`/`COMPLETED`/`FAILED`)으로 구분한다.
- **FR-029**: 같은 참여 제출이 반복되어도 화면은 한 번 반영된 결과를 보여줘야 하며 반복을 오류로 보여서는 안 된다.
- **FR-030**: 참여·수량 변경·참여 취소가 성공하면 상세의 수치(확보·남은 수량, 내 참여, 상태)가 즉시 최신으로 보여야 한다.

**내 활동 (S08)**

- **FR-031**: 내 활동은 '내가 연 공구'와 '내가 참여한 공구' 두 탭으로 나뉘고, 항목마다 상태 뱃지가 붙으며, 더 보기로 이어서 불러오고, 항목을 누르면 상세로 가야 한다.

### Key Entities

- **화면 상태(View state)**: 불러오는 중, 비어 있음, 오류, 정상 중 하나. 모든 데이터 화면이 공통으로 가진다.
- **로그인 세션(Session)**: 현재 사용자가 로그인했는지, 누구인지(표시 이름). 화면에서는 이 둘만 알며 이메일·비밀번호를 보관하지 않는다.
- **공구 카드/상세(GroupBuy view)**: 서버가 내려준 공구 표시용 데이터. 상태 뱃지, 진행률, 역할별 정보(내 참여, 개설자 여부, 명단, 오픈채팅 링크)를 포함한다.
- **폼 오류(Field error)**: 필드 이름과 사유의 쌍. 서버 응답의 필드 이름과 폼 필드를 1:1로 잇는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 처음 방문한 사용자가 로그인 없이 목록을 열어 원하는 공구를 찾기까지 안내 없이 1분 이내에 도달한다(테스트 사용자 3명 이상 관찰).
- **SC-002**: 신규 사용자가 가입 신청부터 인증, 로그인, 첫 참여까지 5분 이내에 마친다(메일 도착 대기 제외, 테스트 사용자 3명 이상 관찰).
- **SC-003**: 휴대폰 폭(360px)에서 모든 화면(S01~S08)에 가로 스크롤이 없고, 주요 버튼이 한 손으로 누를 수 있는 크기다.
- **SC-004**: 서버가 돌려줄 수 있는 모든 입력 오류가 해당 필드 옆에 표시되고, 필드에 매핑되지 않아 사라지는 오류는 0건이다.
- **SC-005**: 비로그인으로 보호된 화면을 연 시도 100%가 로그인 화면으로 가고, 로그인 후 100% 메인(목록)으로 돌아간다.
- **SC-006**: 4G 환경에서 목록 첫 화면이 3초 이내에 보이고, 이후 조건 변경 결과가 1초 이내에 보인다(서버 응답 시간 포함).
- **SC-007**: 참여 제출을 연타해도 화면에 반영되는 참여는 1건이고, 거부 사유 4종(수량 부족, 마감, 끝난 모집, 가격 변경)이 각각 구분된 안내로 100% 보인다.
- **SC-008**: 오픈채팅 링크와 참여자 명단은 서버가 내려주지 않은 사용자에게 0건 노출된다.
- **SC-009**: 모든 시각 표시가 한국 시각이고, 서버 전송 시각이 오프셋 포함 형식인 비율이 100%다.

## Assumptions

- 화면은 기숙사생이 에브리타임 글의 링크를 휴대폰으로 여는 것을 가정한 **모바일 우선 웹**이다. 별도 앱은 만들지 않는다.
- 기술 선택은 설계에서 정했다: 단일 페이지 웹 앱(React, Vite), 같은 저장소의 `frontend/` 폴더, 기존 REST API를 그대로 사용한다. 이 spec은 화면 동작을 규정하고 세부 구조는 plan에서 정한다.
- 이 기능은 서버를 바꾸지 않는다. 필요한 응답 필드(표시 상태, 내 참여, 개설자 여부 등)와 오류 형식은 001, 002, 003, 004의 계약을 따른다. 계약에 없는 것이 필요해지면 해당 기능의 계약을 고치는 별도 결정으로 다룬다.
- 로그인 상태의 유지 방식(세션/토큰)은 002 plan에서 정한다. 이 기능은 '로그인 여부와 표시 이름을 알 수 있고, 거부되면 로그인으로 보낸다'까지만 전제한다. 그 전까지 임시 식별(`X-Member-Id`)은 개발용이며 공개 배포하지 않는다.
- 에브리타임 링크로 들어온 사람은 로그인 후 메인에서 그 공구를 직접 찾는다(G03 결정). 불편하면 원래 링크로 복귀하도록 바꾸는 것은 후속 결정이다.
- **개설자 관리 화면(S09: 참여자별 입금·수령 체크)은 이 spec의 범위 안이다.** 006 계약 기준으로 체크표(필터 전체/미입금/미수령, 입금·수령 체크, 진행 요약)를 구현한다.
- **알림 화면(S10)은 이 spec의 범위 안이다.** 007 계약 기준으로 앱 안 알림함(목록, 읽지 않은 수, 읽음 처리)을 구현한다.
- 실시간 갱신(푸시, 폴링)은 하지 않는다. 사용자가 다시 불러올 때 최신 값이 보인다.
- 상품 이미지, 다국어, 다크 모드, 접근성 인증 수준의 대응, 오프라인 사용, 설치형 웹 앱(PWA)은 이 단계에서 다루지 않는다. 다만 기본적인 키보드 조작, 입력 레이블, 충분한 명암 대비는 지킨다.
- 지원 브라우저는 최근 2년 안에 나온 휴대폰의 기본 브라우저(iOS Safari, Android Chrome)와 데스크톱 최신 Chrome이다.
- 설계 단계에서는 화면 구현을 하지 않는다. 구현은 헌법의 단계 순서에 따라 로그인(4단계) 직전·이후에 사용자가 직접 한다.
