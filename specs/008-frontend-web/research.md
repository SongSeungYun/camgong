# Research: 모바일 우선 웹 화면

방식(모바일 우선 웹 + PWA)과 스택(React + Vite + TypeScript)은 2026-10-27 사용자가 확정했다. 아래 결정 3~14는 **추천안 기준 가안이며 `상태: 사용자 결정 대기`**다. 각 결정에 후보, 추천, 이유, 설명 체크를 적었고 plan·data-model·contracts·quickstart는 추천안 기준으로 썼다. 다른 후보를 고르면 해당 문서를 같이 고친다.

## 스펙·계약 보완 필요 (spec은 수정하지 않았음)

설계 중에 발견한 공백이다. 반영 전까지 구현 착수를 막는 것은 1·4번이다.

1. **PWA 문구 충돌 (착수 전 필요)**: spec 가정 "설치형 웹 앱(PWA)은 이 단계에서 다루지 않는다"는 2026-10-27 결정(PWA, 홈 화면 추가)과 충돌한다. 제안 문구: "홈 화면에 추가할 수 있는 PWA로 제공한다(매니페스트와 아이콘). 오프라인 사용과 푸시는 다루지 않는다." 같은 가정의 "구현은 … 사용자가 직접 한다"도 2026-10-27 작업 방식(세션이 구현하고 사용자가 승인)과 어긋나므로 정리가 필요하다.
2. **S09·S10의 사용자 스토리와 FR이 없다.** 범위에는 들어왔지만(2026-10-27) 시나리오·FR·SC가 없어 tasks를 만들 근거가 약하다. 제안: 사용자 스토리 6(체크표), 7(알림함)을 P3로 추가. FR 초안은 아래 '제안 FR'.
3. **알림함의 진입점이 정해지지 않았다.** 제안: 모든 로그인 화면의 상단 헤더에 벨 아이콘 + 읽지 않은 수 배지(`GET /api/notifications/unread-count`, 화면 이동 시 한 번 조회, 폴링 없음 — spec "실시간 갱신 없음"과 일치).
4. **CSRF 방식이 계약에 없다 (착수 전 필요)**: 002 계약은 세션 쿠키(`SameSite=Lax`)만 말하고, 상태를 바꾸는 요청(POST/PUT/DELETE)에 CSRF 토큰 헤더가 필요한지 정하지 않았다. Spring Security를 쓰면 기본이 켜져 있다. 후보: (A) 같은 출처 + `SameSite=Lax` + `Origin` 검증으로 토큰 없이 방어, (B) 이중 제출 쿠키(`XSRF-TOKEN` 쿠키 → `X-XSRF-TOKEN` 헤더). 프론트는 (B)면 fetch 래퍼에 헤더를 붙여야 한다. **002 계약에 결정을 적어야 한다.**
5. **오류 코드 문구는 계약의 코드 표(`docs/architecture.md` 6.1)에 대응해야 한다.** `UNAUTHENTICATED`(401)는 표에 있으나 002 계약 본문의 오류 표에 아직 없다.
6. 목록 응답에 `participantCount`가 없다(상세에만 있음). 카드는 진행률(확보/총)만 보이므로 문제는 아니다.

**제안 FR (S09·S10, spec에 아직 없음)**

- 체크표(S09): 개설자는 모집 완료 공구의 상세에서 체크표로 이동한다. 표는 참여자별 이름·수량·금액·입금 확인·수령 확인을 보이고, 전체/미입금/미수령 필터와 요약(입금 완료 인원, 수령 완료 인원, 금액)을 보인다. 입금·수령은 각각 켜고 끌 수 있고(되돌리기), 처리 중에는 해당 행 버튼이 비활성화되며, 입금 확인 없이 수령이 확인된 행은 구분해 표시한다. 모집 완료가 아니거나 개설자가 아니면 체크표는 열리지 않고 서버 안내를 보여준다. 체크는 알림을 보내지 않는다.
- 알림함(S10): 로그인 화면의 헤더에 읽지 않은 수 배지를 보이고, 알림함은 최근 순 목록('더 보기')에 유형별 문구(모집 완료, 모집 실패, 정보 수정(바뀐 항목 이름), 공구 취소)와 시각을 보인다. 항목을 누르면 읽음 처리 후 상세로 이동하고, 취소된 공구 알림은 이동하지 않고 내용만 보인다. 이동 불가 알림도 읽음 처리할 수 있다.

## 결정

### 1. 방식: 모바일 우선 웹 + PWA — 상태: 확정 (2026-10-27, 사용자)

에타 링크로 설치 없이 들어오는 것이 핵심 유입이라 웹이 맞고, 홈 화면 추가를 위해 PWA 매니페스트를 둔다. 네이티브 앱 제외. 푸시는 앱 안 알림함으로 대체(007 spec 결정).

### 2. 스택: React + Vite + TypeScript — 상태: 확정 (2026-10-27, 사용자)

후보였던 Vue, Next.js는 선택하지 않았다. SPA라 Spring과 분리하기 단순하고 PWA 플러그인·목 서버 자료가 많다.

### 3. 라우팅 — 상태: 사용자 결정 대기

- **후보**: A. React Router(데이터 라우터) / B. TanStack Router / C. 직접 구현.
- **추천: A.** 가장 흔하고 지연 로딩·보호 라우트·스크롤 복원·쿼리 문자열 지원이 모두 기본이다. B는 타입 안전이 좋지만 이 규모에서 얻는 이득이 작다.
- **새 의존성 이유 (한 줄)**: React Router — 화면 10개의 주소, 로그인 가드, 목록 조건의 주소 반영(FR-015)을 검증된 구현으로 하기 위해.
- **설명 체크**: 목록 조건을 컴포넌트 상태가 아니라 주소 쿼리에 두면 새로고침·공유·뒤로 가기에서 무엇이 달라지는가?

### 4. 서버 데이터 관리 — 상태: 사용자 결정 대기

- **후보**: A. TanStack Query / B. SWR / C. 수제 `useEffect` + `fetch` 훅.
- **추천: A.** '더 보기'는 `useInfiniteQuery`, 참여·수정 후 상세 즉시 최신화(FR-030)는 쿼리 무효화, 로딩·오류·빈 상태 구분(FR-007)과 재시도 정책이 내장이다. 쿼리 키를 `[목록, 조건]`으로 두면 상세에서 돌아와도 캐시가 남아 위치가 유지된다(FR-015).
- **주의**: 캐시된 내 정보가 로그아웃 후 남지 않도록 로그아웃·401 시 캐시를 전부 비운다(FR-003, US2-7).
- **새 의존성 이유 (한 줄)**: TanStack Query — 무한 목록, 변경 후 무효화, 로딩·오류 상태를 직접 짜면 화면마다 중복되기 때문.
- **설명 체크**: 로그아웃 때 쿼리 캐시를 비우지 않으면 어떤 개인 정보가 어디에 남는가?

### 5. API 클라이언트와 타입 — 상태: 사용자 결정 대기

- **후보**: A. 얇은 수제 `fetch` 래퍼 + 계약에서 옮겨 적은 TypeScript 타입 / B. OpenAPI 생성 타입 / C. 런타임 스키마 검증(zod) 병행.
- **추천: A.** 백엔드에 OpenAPI가 없고 계약이 마크다운이라 B는 전제가 없다. 래퍼가 하는 일: `credentials: 'include'`, 오류 본문(`ProblemDetail` + `errors[]`)을 `ApiError`로 변환, 401이면 인증 만료 이벤트 발행, 5xx는 일반 오류로 변환. 알 수 없는 상태 값(FR-008)은 타입 가드로 `'UNKNOWN'` 처리하고 zod 같은 새 의존성은 쓰지 않는다. 계약이 바뀌면 타입과 목 핸들러를 같이 고친다(`contracts/ui-api-map.md`가 기준표).
- **설명 체크**: 서버가 모르는 `status` 값을 주면 화면은 어디서 어떻게 막아야 하는가?

### 6. 폼과 서버 필드 오류 매핑 — 상태: 사용자 결정 대기

- **후보**: A. React Hook Form / B. 제어 컴포넌트 수제 / C. 폼 라이브러리 + 스키마 검증.
- **추천: A.** 개설 폼이 필드 10개이고 서버 `errors[{field,message}]`를 같은 이름의 필드 옆에 한 번에 표시(FR-005)하려면 `setError(field, …)`와 입력값 유지가 필요하다. 서버 필드 이름은 계약의 요청 본문 필드와 같게 폼 필드 이름을 맞춘다. 매핑되지 않는 필드는 폼 상단 오류로 모은다. 클라이언트 검증은 안내용(범위 표시)이고 최종 판단은 서버다.
- **새 의존성 이유 (한 줄)**: React Hook Form — 필드 10개 폼의 입력 유지, 서버 필드 오류 매핑, 제출 중 비활성화를 간결하게 하기 위해.
- **설명 체크**: 클라이언트 검증을 통과해도 서버가 거부할 수 있는 경우는 무엇이고, 그때 입력값은 왜 지워지면 안 되는가?

### 7. 스타일링 — 상태: 사용자 결정 대기

- **후보**: A. CSS Modules + CSS 변수(디자인 토큰) / B. Tailwind CSS / C. 컴포넌트 라이브러리(MUI 등).
- **추천: A.** 새 의존성이 없고(Vite 기본 지원), 화면 10개 규모에서 충분하다. 모바일 우선 `min-width` 미디어 쿼리, 터치 대상 최소 44px(SC-003), 읽기 폭 제한 중앙 정렬(데스크톱, spec 엣지 케이스)을 `shared/ui`에서 한 번 정한다. B는 빠르지만 클래스 문자열이 길어지고 설정이 늘어난다. C는 번들이 크고 모바일 UI 취향이 갈린다.
- **설명 체크**: 모바일 우선(`min-width`)으로 쓰면 데스크톱 폭에서 레이아웃이 깨지지 않는 이유는?

### 8. 목(mock) 서버 — 상태: 사용자 결정 대기

- **후보**: A. MSW(브라우저와 Vitest 둘 다 같은 핸들러) / B. json-server 등 별도 프로세스 / C. 목 없이 처음부터 실제 백엔드.
- **추천: A.** 핸들러가 계약의 응답 표와 같은 모양을 돌려주고, 시나리오 데이터(남은 수량 부족, 가격 변경, 마감, 인증 만료)를 토글할 수 있다. 개발 서버에서는 `VITE_USE_MOCK=true`일 때만 켠다. **위험**: 목이 계약에서 벗어나면 통과하는 화면이 실제에서 깨진다. 완화: 핸들러 응답 모양을 `ui-api-map.md`와 대조하고, 백엔드 기능이 구현될 때마다 quickstart를 실제 백엔드로 다시 돌린다.
- **새 의존성 이유 (한 줄)**: MSW — 백엔드 없이 화면과 테스트를 계약 응답으로 개발하기 위해.
- **설명 체크**: 목이 계약과 달라졌을 때 어느 단계에서 어떻게 발견되는가?

### 9. 테스트 — 상태: 사용자 결정 대기

- **후보**: A. Vitest + Testing Library(화면) + Playwright(핵심 시나리오 3~4개, 360px) / B. 단위 테스트만 / C. 테스트 없음.
- **추천: A.** 헌법 IV의 필수 대상은 백엔드지만 프론트도 FR-005(필드 오류 위치), FR-021(역할별 버튼), FR-029(연타), SC-003(가로 스크롤 없음)은 자동으로 잡을 가치가 있다. 단위/화면 테스트는 MSW 핸들러를 재사용한다. Playwright는 로그인 → 목록 → 참여, 개설 필드 오류, 360px 가로 스크롤 없음, 인증 만료 리다이렉트 정도로 최소화한다.
- **설명 체크**: 화면 테스트가 통과해도 실제 백엔드와 안 맞을 수 있는 이유와, 이를 줄이는 방법은?

### 10. 인증 처리와 같은 출처 — 상태: 사용자 결정 대기

- **후보**: A. 앱 시작 시 `GET /api/auth/me`로 로그인 여부 확인, 모든 요청에 쿠키 포함, 401이면 캐시 비우고 로그인 화면으로 / B. 로그인 응답을 `localStorage`에 저장해 판단.
- **추천: A.** 쿠키는 `HttpOnly`라 스크립트가 읽을 수 없고(XSS 방어), 서버가 세션의 유일한 진실 원천이다. 화면은 `me`의 `{id, displayName}`만 보관한다(메모리 상태, 새로고침 시 다시 조회). 개발에서는 Vite 프록시(`/api` → 백엔드)로 **같은 출처**를 만들어 `SameSite=Lax` 쿠키가 동작하게 하고, 운영도 같은 출처(리버스 프록시)여야 한다(결정 13). 보호 라우트는 `me`가 오기 전에 깜빡이지 않게 '확인 중' 상태를 둔다.
- **설명 체크**: 토큰을 `localStorage`에 두는 방식에 비해 `HttpOnly` 쿠키가 XSS에 안전한 이유와, 대신 CSRF를 신경 써야 하는 이유는?

### 11. 시각 처리 — 상태: 사용자 결정 대기

- **후보**: A. 브라우저 내장 `Date`/`Intl.DateTimeFormat`(`timeZone: 'Asia/Seoul'`)만 사용 / B. date-fns(-tz) / C. dayjs.
- **추천: A.** 입력(`datetime-local`)은 KST로 해석해 `+09:00` 오프셋을 붙인 ISO 문자열로 서버에 보내고, 표시는 `Intl`로 KST 포맷한다. 남은 시간은 불러온 시점 기준 계산(spec: 실시간 갱신 없음). 사용자의 기기 시간대와 무관하게 동작해야 하므로 기기 시간대를 가정하는 `toLocaleString()` 기본값을 쓰지 않는다(FR-004). 라이브러리가 필요 없는 규모다.
- **설명 체크**: 기기 시간대가 UTC인 사용자가 `datetime-local`에 입력한 값을 `new Date(value)`로 보내면 무엇이 틀어지는가?

### 12. 목록 조건·스크롤 복원 — 상태: 사용자 결정 대기

- **후보**: A. 조건(`status`, `category`, `q`, `sort`)을 주소 쿼리에 두고 라우터가 읽는다 + 쿼리 캐시로 목록 위치 유지 / B. 컴포넌트 상태 + `sessionStorage` / C. 전역 상태 저장소.
- **추천: A.** FR-015(새로고침·공유에서 유지)를 자연스럽게 만족하고 별도 저장소가 필요 없다. 검색어 입력은 디바운스 후 주소에 반영하고(키 입력마다 요청하지 않음), 조건이 바뀌면 커서를 버리고 처음부터 다시 불러온다. 상세에서 돌아올 때 '더 보기'로 이미 불러온 페이지는 쿼리 캐시에서 복원한다("가능한 한" 유지, spec). 서버가 400을 주는 잘못된 주소 값(주소 직접 편집)은 기본 조건으로 되돌린다.
- **설명 체크**: 조건이 바뀌었는데 이전 `nextCursor`를 그대로 쓰면 서버는 어떻게 응답하는가(003 계약)?

### 13. 배포 형태 — 상태: 사용자 결정 대기 (4단계 Docker와 함께)

- **후보**: A. 리버스 프록시(nginx/Caddy) 한 도메인: `/api` → Spring, 그 외 → 정적 빌드 / B. 정적 빌드를 Spring이 직접 서빙 / C. 프론트를 별도 도메인에 정적 호스팅.
- **추천: A.** 같은 출처라 `SameSite=Lax` 쿠키와 CSRF 방어가 단순해지고(결정 10, 계약 공백 4), PWA 서비스 워커의 범위(scope)도 한 출처에 둔다. C는 CORS와 `SameSite=None; Secure`가 필요해 복잡하다. 결정은 4단계(Docker)에서 하고, 그전 개발은 Vite 프록시로 같은 출처를 흉내 낸다.
- **설명 체크**: 프론트와 API가 다른 출처이면 쿠키 로그인에서 무엇이 추가로 필요해지는가?

### 14. 범위 축소 순서와 PWA 상세 — 상태: 사용자 결정 대기

- **범위 축소(헌법 I, 일정이 막힐 때)**: S10 알림함 → S09 체크표 → S08 내 활동 순으로 줄인다. S01~S07(가입·로그인·목록·상세·개설·수정·참여)은 줄이지 않는다.
- **PWA 상세**: 매니페스트(이름, 아이콘, `display: standalone`, 시작 URL, 테마 색) + 서비스 워커는 **등록하되 오프라인 캐시는 하지 않음**. 이유: spec이 오프라인을 제외했고, 낡은 앱 셸이 배포 후 남는 문제(오래된 화면이 새 계약을 못 따라감)를 피한다. `vite-plugin-pwa`는 자동 업데이트 모드(새 버전이 있으면 다음 로드에 교체). 설치 가능성(홈 화면 추가)은 HTTPS가 필요하다(운영, 개발은 localhost 예외).
- **새 의존성 이유 (한 줄)**: `vite-plugin-pwa` — 매니페스트·서비스 워커 생성을 직접 쓰지 않고 검증된 설정으로 하기 위해.
- **설명 체크**: 서비스 워커가 앱 셸을 캐시하면 배포 후 어떤 사용자가 옛 화면을 계속 보게 되는가?
